# かけら 要件定義書

version 1.0 / 2026-07-31

本書は何を作るかを定める。見た目と文言は DESIGN.md、配置と運用は DEPLOY.md、コードの置き場所は STRUCTURE.md に定義する。

---

## 0. 前提

### 0.1 このアプリは何のためにあるか

**自分の中でまだ何かが動いていることを、あとから確認できるようにするため。**

「したいことがない」「何かに興味が持てない」という状態にいる人は、内省して答えを探しても出てこない。関心や欲求は、考えて発見するものではなく、何かに反応した瞬間として先に現れ、後から気づかれるものだからである。

したがってこのアプリの役割は、**判断の前に材料を集めること**に限定される。集めるのは三つ。

1. **心が動いたこと** — 反応が出た瞬間の記録。良いことでなくてよい
2. **片づけた面倒 / 関わった人** — 自分への信用を戻す実績と、他者との接点の事実
3. **月に一度の外出** — 反応が起きる機会を、こちらから作りにいく

集めた材料の解釈は、一定期間が経つまで行わない。

### 0.2 想定ユーザー

自分の行動を絶えず採点し、基準に届かない自分を減点してしまう人。
したがって、**達成・継続・不足を可視化する機能は、この製品では害として扱う**（第2章）。

記録はすべて本アプリ内で完結する。外部のノートアプリや表計算での併用を前提としない。

### 0.3 段階（フェーズ）

このアプリは段階的に育てる。**本書の要件には、恒久的に守るものと、その段階に限って有効なものが混在する。** 各要件の適用範囲を次の記号で示す。

| 記号 | 意味 |
|---|---|
| **［不変］** | 全段階で守る。段階が進んでも緩めない |
| **［P1］** | 第1段階に限って有効。第2段階で置き換わる |
| **［P2〜］** | 第2段階以降に適用 |

| 段階 | 形 | 保存先 | 認証 | 実行環境 | 目的 |
|---|---|---|---|---|---|
| **P1** | 静的 Web アプリ | 端末内（localStorage） | なし | なし（静的配信のみ） | 設計そのものが成立するかを確かめる |
| **P2** | Web アプリ ＋ API ＋ DB | AWS 上の DB（端末はキャッシュ） | **必須** | **Docker（Laravel / EC2）** | 端末をまたいで確実に残す。機種変更・データ削除で失わない |
| **P3** | ＋ PWA Push | 同上 | 同上 | 同上 | 就寝前の通知 |

**P2 からはログインを必須とする。** 端末内保存だけでは、ブラウザのデータ削除や機種変更で二か月分が一度に失われる。記録が残ることは、この製品の前提そのものである。

ただし、**最初の一行を書く前に登録を求めてはならない**（P2-1.7）。開いて十秒で書けることは登録より優先される。

第1段階の実装が、第2段階で捨てる前提の使い捨てにならないよう、保存層は最初から driver として分離する（NFR-8.1）。

### 0.4 不変条件

段階が進んでも変えないもの。**［不変］**

1. 第2章の禁止要件（NG-1〜NG-11）
2. サーバー側で記録内容を解析・集計・学習に使わない
3. 記録内容を第三者へ渡さない。広告・解析タグを入れない
4. 登録に求める個人情報はメールアドレス1件のみ。最初の一行を書く前に登録を求めない
5. 記録は書いた本人のものであり、いつでも全件を持ち出せること

## 1. 機能要件

### 画面構成

**「今日」を根とした一本道とする。タブ（常時表示のナビゲーション）を置かない。** 根拠と詳細は UX.md に定める。

| 画面 | 役割 | 到達方法 |
|---|---|---|
| 今日 | その日の一行を記録する。起動時の初期画面であり、すべての戻り先 | 起動時 |
| ひとつ | 今月の外出をひとつ決める／書き換える | 「今日」の置いたあとの画面に出る一行から |
| かけら | 記録を見る。開放前は直近7日のみ | 「今日」の最下部の入口から／開放の報せから |
| このアプリについて | 保存先の説明・控え・やめる | 「かけら」の最下部から |

「ひとつ」は日々の画面に常駐しない。**用がある日にだけ**、記録を置いたあとの画面に一行で現れる（FR-3.11）。低頻度の機能が常時見えていること自体が、達成状況の可視化として働くためである。

| FR-1.7 | 1日1レコード。同日中は何度でも上書きできる | 必須 |

### FR-3 ひとつ（月に一度の外出）

反応が起きるのを待つのではなく、機会を作りにいくための機能。**目的地に着くことではなく、家を出ることが目的**である。

| ID | 要件 | 優先 |
|---|---|---|
| FR-3.1 | 月ごとに1件だけ「目的」を登録できる（1行、最大60字） | 必須 |
| FR-3.2 | 例を示す。「◯◯を食べる」「銭湯に入る」など、体力を使わず達成が一目で分かるもの | 必須 |
| FR-3.3 | 予定日を任意で設定できる（未設定でよい） | 中 |
| FR-3.4 | 「行った」の1タップで記録できる。記録されるのは押した日付のみ | 必須 |
| FR-3.5 | 目的は月の途中で何度でも書き換えられる | 必須 |
| FR-3.6 | 「目的は家を出るための口実であり、途中で捨ててよい」旨を画面に常時表示する | 必須 |
| FR-3.7 | 月が変わると新しい枠が現れる。前月が未実行でも、表示・通知・履歴のいずれにも残さない | 必須 |
| FR-3.8 | 実行済みの月と未実行の月を並べて比較できる画面を作らない | 必須 |
| FR-3.9 | 開放前は今月ぶんのみ表示する。過去の外出は開放後に一覧できる | 中 |
| FR-3.10 | 目的が未登録の月は、催促ではなく提案として表示する（「今月のひとつを決めますか」）。表示場所は記録を置いたあとの「今日」の画面とする | 中 |
| FR-3.11 | 「ひとつ」への入口を「今日」の画面の最下部に常時置く。ラベルは「今月のひとつ」とし、**決めていない／行っていないという状態を一切示さない**。「これまでを見る」と対で左右に並べ、同じ書式にする | 必須 |
| FR-3.12 | それとは別に、その日の記録がある「今日」の画面に、今月の状態に応じて次を出す | 必須 |

**FR-3.12 の表示規則**

| 今月の状態 | その日の記録がある「今日」の画面に出るもの |
|---|---|
| 目的が未登録 | **何も出さない**（最下部の「今月のひとつ」で足りる） |
| 目的が登録済み・未実行 | `◇ ＜目的＞` と「行った」（その場で押せる。画面遷移しない） |
| 実行済み | **何も出さない** |

- 「今月のひとつを決めますか」という提案は出さない。常時の入口がある以上、毎日誘えば催促になる
- 保存直後だけでなく、記録済みの日に開き直したときも出す。朝に記録を置き、夕方に外出した人が「行った」を押せなくなるため
- 実行済みの月を再掲しないのは、済んだことの再表示が達成の表示に近づくため。行った事実は「かけら」の該当日に印として残る（FR-2.9）
- 入口のラベルに件数・状態・色の差を付けない。**扉があるだけで、中の状況を外から見せない**

> FR-3.7・FR-3.8 は重要。行かなかった月が可視化された時点で、この機能は達成率の表示に変わる。

### FR-4 はじめて（初回説明）

一般ユーザーは、7日しか見えないことや60日の開放を知らずに触れる。初回のみ説明を出す。

| ID | 要件 | 優先 |
|---|---|---|
| FR-4.1 | 初回起動時に1画面だけ説明を表示する。3項目以内、スクロール不要 | 必須 |
| FR-4.2 | 内容は2つ。(a) 何を書くのかが分かる具体 (b) 消えてしまう前に一日一行拾うこと。**説明を足さない。削れる語は削る**（DESIGN.md 第7章の文面を用いる） | 必須 |
| FR-4.10 | 「このアプリについて」の先頭に「使い方」の節を置く。初回説明では説明しないぶん、ここに書く | 必須 |
| FR-4.11 | 初回に「このアプリについて」を開いたときは、最下部に本編へ進む操作（「はじめる」）を置く。2回目以降に開いたときは置かない | 必須 |
| FR-4.9 | 次の3つは初回説明に置かない。いずれも本編の画面で足りるため。<br>・「なし」でよいこと → 入力画面の「なし」ボタンと補助文<br>・二か月後に読み返せること → かけら画面の「これより前は、二か月後に読み返せます」<br>・保存先と通知 → 「このアプリについて」 | 必須 |
| FR-4.8 | 説明に、作り手側の用語・抽象語を使わない（「反応した瞬間」「手がかり」等）。読む人が自分の経験として分かる言葉で書く。機能の列挙ではなく、**書かなければその瞬間が消えること**を伝える（DESIGN.md 第7章） | 必須 |
| FR-4.6 | 画面名（「はじめて」等）を見出しとして出さない。最初に読ませるのは目的である | 必須 |
| FR-4.7 | 保存先の説明と、端末標準のリマインダーの案内は初回説明に置かず、「このアプリについて」に置く | 必須 |
| FR-4.3 | 「はじめる」を押すと「このアプリについて」を開き、そこから本編（今日）へ入る。以後、初回説明は表示しない。再表示の導線は「かけら」画面下部と「このアプリについて」に置く | 必須 |
| FR-4.4 | 初回説明の時点で登録・権限要求を行わない。登録を求めるのは最初の記録を保存したあと（P2-1.7） | 必須 |
| FR-4.5 | 複数ページのチュートリアルやツアーを作らない | 必須 |

端末内保存のみの P1 では消失への唯一の手当てであり、P2 以降も「本人が全件を持ち出せること」（不変条件5）として残す。ただし**内容は画面に出さない**（FR-2.1 を迂回させない）。

| ID | 要件 | 優先 |

| FR-5.1 | 全データを JSON ファイルとして端末に保存できる。ファイル名は `kakera-YYYY-MM-DD.json` | 必須 |
| FR-5.2 | 控えの取得時、記録内容を画面に表示しない | 必須 |
| FR-5.3 | 控えファイルから復元できる。同一日が衝突した場合は端末側を優先する | 必須 |
| FR-5.4 | 不正なファイルを読み込んだ場合、既存データを壊さず、読めなかった旨のみ表示する | 必須 |
| FR-5.5 | 記録が端末内にのみ存在することを画面に明記する | 必須 |

### FR-6 やめる

記録を編集・削除する機能ではない。**このアプリを使うのをやめるための出口**である。

かけらは拾って置いておくものなので、一部だけ捨てられるようにはしない。都合の悪い日を消せると、記録が編集された自己像に変わり、材料としての価値が失われる。
一方で、まるごとやめる手段は必要である。理由は三つ。(a) 端末を人に渡すとき (b) 使うのをやめると決めたとき (c) 自分の記録を自分で処分できないアプリは、記録が本人のものだという不変条件（0.4-5）に反するため。

ただしこの操作は、**自分を責めている最中に押されやすい**。落ち込んだ日に「こんな記録に意味がない」と消してしまえば、二か月分の材料が一度に失われる。したがって、機能としては置くが、勢いで到達できない場所に置く。

| ID | 要件 | 優先 |
|---|---|---|
| FR-6.1 | 部分削除（特定の日・特定の月だけ消す）を提供しない | 必須 |
| FR-6.2 | 全消去は提供する。ただし主要画面に置かず、「このアプリについて」の最下部にのみ配置する | 必須 |
| FR-6.3 | 実行前に控え（FR-5）の取得を経由させる。控えを取らずに進む選択肢は残すが、既定は取る側とする | 必須 |
| FR-6.4 | 確認は2段階とし、2段階目は取り消せない旨を明示する | 必須 |
| FR-6.5 | 実行後は初回状態に戻る。「消しました」以上の文言を出さない | 必須 |
| FR-6.6 | 消去を促す導線・提案・整理機能を作らない | 必須 |
| FR-6.7 | ［P2〜］退会は7日間の猶予を置く。猶予中に再ログインすれば取り消せる。猶予後にサーバー上のデータを完全削除する | 必須 |

> FR-6.3 の意図：やめる判断そのものは尊重する。ただし、判断と同時に材料まで失う必要はない。手元にファイルが残っていれば、後から気が変わったときに戻せる。

### FR-8 今日の一言

保存後の画面に、日ごとに異なる短い一文を表示する。毎日まったく同じ画面が返ってくると、記録を置いた日と置かなかった日の区別が体感として消え、開く理由がなくなるため。

ただしこの一文は、**書いた行為への評価であってはならない**。称賛すれば FR-1.9 に反し、励ませば継続を求めることになる。したがって内容は**その日の暦から決まる観察**とし、ユーザーの行動によって変化しない。

| ID | 要件 | 優先 |
|---|---|---|
| FR-8.1 | 保存完了時、記録カードの下に一文を表示する | 必須 |
| FR-8.2 | 表示する一文は日付から一意に決まる。ユーザーの記録内容・継続日数・実行状況に依存しない | 必須 |
| FR-8.3 | 一年分（366日）を静的データとして持ち、日付をキーに引く | 必須 |
| FR-8.4 | 同じ日に記録を書き直しても、一文は変わらない | 必須 |
| FR-8.5 | 一文は保存後の画面にのみ表示する。起動時・一覧・その他の画面には出さない | 必須 |
| FR-8.6 | 過去の一文を見返す画面・一覧・収集要素を作らない | 必須 |
| FR-8.7 | データが欠けている日は何も表示しない（代替文を出さない） | 中 |
| FR-8.8 | 文言の執筆規則は DESIGN.md「今日の一言」に従う | 必須 |

> FR-8.6 の意図：集められるようにした時点で、一文が収集対象になり、記録が言葉を得るための手段に変わる。読めるのはその日一度きりとする。

> FR-8.2 の意図：行動に応じて内容が変われば、それは評価である。日付だけで決まる＝**何を書いても、書かなくても、同じものが待っている**という状態を保つ。

## 2. 実装しない要件（禁止要件）

意図的に持たない機能。将来の版でも追加しない。

| ID | 実装しないもの | 理由 |
|---|---|---|
| NG-1 | 連続日数（ストリーク）、記入率、達成率 | 途切れた時点で失敗の記録に変わる |
| NG-2 | グラフ、集計、スコア、バッジ、レベル | 記録が競技になる |
| NG-3 | 繰り返しの督促通知、未記入の警告 | 書かなかったことを責める装置になる |
| NG-4 | 「一年前の今日」等の自動振り返り | 解釈を先送りする設計に反する |
| NG-5 | SNS共有、他ユーザーとの比較、ランキング | 見せるために書く記録になる |
| NG-6 | 感情のラベル選択（5段階評価・アイコン選択） | 選択肢が反応を先に規定する |
| NG-7 | AI による分析・要約・助言 | 材料が集まる前に解釈が入る |
| NG-8 | 広告、行動計測タグ | 記録の内容が外部と関わる余地を作らない |
| NG-9 | 外出の実行率・未実行月の一覧 | FR-3 が達成率の表示に変わる |
| NG-10 | 開放までの残り日数カウントダウン | 進捗メーターとして働く |
| NG-11 | 「今日の一言」の履歴・コレクション・未取得表示 | 記録が言葉を集める手段に変わる |

## 4. データ仕様

```jsonc
{
  "version": 1,
  "started_on": "2026-07-25",          // 初回記録日。開放判定の起点
  "onboarded": true,                   // 初回説明を閉じたか

  "entries": {                         // 日ごとの記録。1日1件
    "2026-07-25": {
      "feeling":    "町ブラ良いなと思った",
      "done":       "歯医者の予約",
      "person":     "◯◯さんが△△と言っていた",
      "created_at": "2026-07-25T22:41:03.120Z"
    }
  },

  "outings": {                         // 月ごとの外出。1か月1件
    "2026-07": {
      "goal":       "◯◯の中華そばを食べる",
      "planned_on": "2026-07-30",      // 任意
      "went_on":    "2026-07-30",      // 未実行なら null
      "created_at": "2026-07-02T21:10:44.001Z"
    }
  }
}
```

| 項目 | 規則 |
|---|---|
| 日付 | 端末のローカル時刻に基づく `YYYY-MM-DD` |
| 月キー | `YYYY-MM` |
| `feeling` | 必須。未入力時は文字列 `"なし"` を格納する |
| 未実行の外出 | `went_on: null` のまま残す。削除も集計もしない |

「今日の一言」はアプリに同梱する静的データ（`lines.json`）であり、ユーザーデータには保存しない。

```jsonc
// lines.json — 月日をキーにした366件
{
  "07-31": "蝉の声が少しずつ入れ替わる頃",
  "08-01": "夕立のあと、道の匂いが変わる"
}
```

### 4.1 第2段階のスキーマ

|---|---|---|
| `id` | uuid | 主キー |
| `email` | text | 一意。認証にのみ使う |
| `started_on` | date | 開放判定の起点 |
| `onboarded_at` | timestamptz | |
| `created_at` / `updated_at` | timestamptz | |

**entries**

| 列 | 型 | 備考 |
|---|---|---|
| `user_id` | uuid | `users.id` |
| `entry_date` | date | `user_id` との複合一意キー |
| `feeling` | text | 必須。未入力時は `"なし"` |
| `done` | text | null 可 |
| `person` | text | null 可 |

| 列 | 型 | 備考 |

## 5. 画面遷移

**「今日」を根とした、行き止まりのある一本道。深さは最大2。戻り先は常に「今日」。**
起動時は必ず「今日」を開く。前回どの画面を見ていたかを覚えない。詳細は UX.md 第4章。

```
  ┌──────────┐  初回のみ
  │ はじめて  │──「はじめる」──┐
  └──────────┘                │
                               ▼
  ╔═══════════════════════════════════╗
  ║              今日                  ║ ◀── 起動時は必ずここ
  ║  （書く前）                        ║
  ║   日付／入力欄／なし／＋ 済・人      ║
  ║   ［記録する］                     ║
  ╟───────────────────────────────────╢
  ║  （置いたあと）                    ║
  ║   記録カード ＋ 今日の一言          ║
  ║   ─ 用がある日だけ、一行 ─          ║
  ║   「今月のひとつを決めますか」 ─────╫──▶ ひとつ
  ║   ◇ 目的 ［行った］                ║      ・今月の目的
  ║   「読み返せます」（開放日のみ）─────╫──▶ かけら
  ║                                   ║
  ║   これまでを見る ──────────────────╫──▶ かけら
  ╚═══════════════════════════════════╝     ・直近7日（開放後は全期間）
                                          │  ・控え／書き出し
                                          ▼
                                 ┌────────────────────┐
                                 │ このアプリについて   │
                                 │ ・はじめての説明     │
                                 │ ・保存先の説明       │
                                 │ ・使うのをやめる     │◀ 最下部
                                 └────────────────────┘
```

- 「行った」はその場で印が変わるだけで、画面遷移しない
- 各画面の左上に戻る導線を置く（「← 今日」「← かけら」）。ブラウザの戻る操作でも同じ動きにする
- `lg` 以上でも1カラムを保ち、複数画面を同時に表示しない（NFR-4）

第2段階では次が加わる。

| 画面 | 出る場面 |
|---|---|
| 登録のお願い | 初回の記録を保存した直後。1回だけ（P2-1.7） |
| ログイン | 2回目以降の起動で未登録の場合、および別端末での初回（P2-1.9） |
| ロック解除 | アプリロックを有効にしている場合の起動時（P2-1.11） |

いずれも「今日」より前には出さない。**最初の一行を書く前に登録・認証の画面を出してはならない。**

## 6. 第2段階（P2）の要件

端末内保存を、AWS 上の DB による同期へ置き換える段階。**P1 の設計思想は変えない。増えるのは保存先だけである。**

### 6.1 前提

| ID | 要件 |
|---|---|
| P2-0.1 | ログインを必須とする。記録はアカウントに紐づき、サーバーを正とする |
| P2-0.2 | 端末内は常にキャッシュとして保持する。通信できない状態でも記録・閲覧ができること |
| P2-0.3 | 通信復帰時に自動で同期する。ユーザーに同期操作を求めない |
| P2-0.4 | 同期の失敗を画面上のエラーとして出さない。端末内に残り、次回に送られることを保証する |
| P2-0.5 | 未登録のまま記録できるのは初回の1回のみ（P2-1.7） |

### 6.2 認証（ログイン）

ログインは必須。理由は二つ。

1. **記録が残ることが前提だから。** 端末内保存だけでは、ブラウザのデータ削除・プライベートモード・機種変更で失われる。二か月かけて集めた材料が一度に消える設計は、この製品では成立しない
2. **鍵のかかった自分の場所になるから。** 誰でも開ける画面ではなく、自分だけが入れる場所であることが、書ける内容の幅に効く

| ID | 要件 |
|---|---|
| P2-1.1 | パスワードを持たない方式とする。第一候補はパスキー、代替としてメールのワンタイムリンク |
| P2-1.2 | 収集する個人情報はメールアドレス1件のみ。氏名・生年月日・電話番号・性別を求めない |
| P2-1.3 | ログイン前に、何のために登録するのか（端末をまたいで残すため）を1行で示す |
| P2-1.4 | ソーシャルログイン（外部サービス連携）を提供しない。記録の存在を他社に知らせないため |
| P2-1.5 | ログアウトしても端末内のキャッシュは即座に消さない。次のログインまで保持する |
| P2-1.6 | 退会時、記録とアカウントを完全に削除する。論理削除で残さない（FR-6.7 の猶予を適用） |
| P2-1.7 | **初回に限り、未登録のまま1件目を記録できる。** 登録を求めるのは保存が完了したあと | 
| P2-1.8 | P2-1.7 で登録した際、端末内の記録をそのままアカウントへ引き継ぐ |
| P2-1.9 | 2回目以降の起動では、登録が完了するまで新規の記録を保存しない |
| P2-1.10 | ログイン状態・メールアドレスの表示は「このアプリについて」内にとどめる。日々の画面に出さない |

> P2-1.7 の意図：初回起動でいきなり登録画面に当たると、この製品を最も必要とする人ほど離脱する。開いて十秒で一行書けることは、登録より優先される。順序は「書く → 残すために登録する」であり、逆にしない。

#### アプリロック

| ID | 要件 |
|---|---|
| P2-1.11 | 起動時の生体認証（パスキー／端末のロック解除）を任意で有効にできる |
| P2-1.12 | 既定は無効。設定から明示的に有効化する |
| P2-1.13 | ロック中は記録の内容を一切表示しない。プレビュー・通知本文にも出さない |

### 6.3 同期

| ID | 要件 |
|---|---|
| P2-2.1 | 同期の単位は日次レコード（`entries`）と月次レコード（`outings`） |
| P2-2.2 | **確定した過去のレコードは不変**。サーバーに既にある日付は上書きしない |
| P2-2.3 | 当日ぶんのみ更新可。更新は同日中に限り、`updated_at` の新しい方を採用する |
| P2-2.4 | 衝突時に「サーバー版／端末版のどちらを残すか」をユーザーに問わない。P2-2.2・2.3 の規則で機械的に決める |
| P2-2.5 | 削除は全件削除のみ（FR-6.1 の継承）。日単位の削除 API を作らない |
| P2-2.6 | 60日の開放判定は `started_on` に基づき、サーバー側で行う |

### 6.4 サーバー側の禁止事項　［不変］

| ID | 要件 |
|---|---|
| P2-3.1 | 記録内容を解析・分類・要約・集計しない |
| P2-3.2 | 記録内容を機械学習の学習データに使わない |
| P2-3.3 | 記録件数・継続日数を集計した指標を、ユーザーに返さない |
| P2-3.4 | 運用者が記録内容を日常的に閲覧できる管理画面を作らない。障害調査は本人の同意を得た場合に限る |
| P2-3.5 | アクセスログに記録内容を出力しない |

### 6.5 暗号化についての決定事項（要判断）

保管時の暗号化方式を、P2 の設計を始める前に決める。

**前提**：パスワードレス（P2-1.1）を採ると、鍵の材料になるパスワードが存在しない。クライアント側で暗号化する場合、鍵をどこから作るかを別途決める必要がある。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A** | サーバー側暗号化のみ（KMS による保管時暗号化） | 実装が単純。復旧不能のリスクがない。パスワードレスと矛盾しない | 運用者が技術的には内容を読める。6.4 は運用ルールによる約束にとどまる |
| **B** | クライアント側暗号化。ログインとは別に、本人だけが知る合言葉を1つ登録してもらい、そこから鍵を作る | 6.4 が約束ではなく技術的な保証になる | 合言葉を失うと復旧できない。登録の手間が増える。端末追加のたびに合言葉の入力が要る |
| **C** | クライアント側暗号化。鍵は端末に保持し、端末追加時は既存端末から移す | 合言葉が不要 | 全端末を失うと復旧できない。端末が1台しかない状態では実質バックアップがない |

**当面は案 A を推奨する。** 理由は、案 B・C の欠点が「二か月ぶんの材料を失う」という、この製品で最も避けたい事態に直結するため。6.4 の禁止事項は運用ルールとして厳格に守り、管理画面を作らない（P2-3.4）ことで実効性を担保する。

案 B を採る場合は、合言葉の紛失時に**記録が完全に失われることを登録時に明示**し、控え（FR-5）の取得を強く促す設計とする。

### 6.6 構成

サーバー構成は **Laravel（Docker / EC2）＋ RDS for PostgreSQL** とする。詳細は DEPLOY.md 第7章に定義する。
4.1 のスキーマは RDS for PostgreSQL 上にそのまま置く。

コンテナ化は P2 からとし、P1 では採らない（NFR-8.8）。P1 の成果物は静的ファイルのみで、実行環境を持たないため。
