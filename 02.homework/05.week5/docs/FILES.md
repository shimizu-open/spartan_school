## 第0章　そもそも Web アプリとは何か

### 0.1 Web ページの正体は「ファイルの束」

ブラウザ（Chrome や Safari）でページを開くと、ブラウザは裏で**どこかのコンピュータからファイルをもらってきて、組み立てて表示している**。もらうファイルは主に3種類。

| 種類 | 拡張子 | 役割 | 喩え |
|---|---|---|---|
| HTML | `.html` | **何があるか**（見出し、入力欄、ボタン） | 家の骨組み |
| CSS | `.css` | **どう見えるか**（色、書体、余白） | 内装・塗装 |
| JavaScript | `.js` | **どう動くか**（押したら保存する、画面を切り替える） | 電気配線と家電 |

このアプリも例外ではない。`かけら` を開いたとき、ブラウザは HTML を1枚、CSS を2枚、JavaScript を十数枚、フォントを十数個受け取って、それを組み立てて画面にしている。

### 0.2 「サーバー」とは

ファイルを配る側のコンピュータを**サーバー**と呼ぶ。このアプリのサーバーは Amazon が貸してくれる置き場（**S3**）と配達網(**CloudFront**)で、そこに完成品のファイル一式を置いてある。詳しくは第8章。

重要なのは、このアプリのサーバーは**ファイルを配るだけ**で、何も計算しないし、何も受け取らないこと。ユーザーが書いた記録は、サーバーには一切送られず、**ユーザー自身のブラウザの中**に保存される（第5章）。これは手抜きではなく、「記録を外に出さない」という要件（REQUIREMENTS.md NFR-7.1）を最も確実に満たす設計である。**送る仕組みがそもそも存在しなければ、漏れようがない。**

### 0.3 このリポジトリの3種類のファイル

リポジトリ（このフォルダ一式）の中身は、役割で3つに分かれる。**ここを取り違えると、何をサーバーに上げるのかが分からなくなる。**

| 種類 | 何か | サーバーに上げる？ |
|---|---|---|
| **① 材料** | 人間が書いたもの。アプリの元 | 上げない |
| **② 完成品** | 材料から機械が組み立てたもの | **これだけ上げる** |
| **③ 道具・書類** | 組み立て方の指示、AWS の設定、仕様書 | 上げない |

```
web/src/  ──[ npm run build ]──▶  web/dist/  ──[ aws s3 sync ]──▶  S3（サーバー）
 ①材料           ③道具              ②完成品
```

料理に喩えると、`src/` が食材、`npm run build` が調理、`dist/` が料理、S3 が客に出す皿。**食材をそのまま客に出すことはない。**

なぜ材料と完成品を分けるのか。材料は「人間が読み書きしやすい形」、完成品は「ブラウザが速く受け取れる形」で、**最適な形が違う**からである。具体的に何が違うのかは第7章（ビルド）で見る。

### なぜこう分けるのか — この構造の一番大事な考え方

このアプリの構造は、一言でいうと**「データは一方通行に流れる」**。

```
  ユーザーが操作する
       │
       ▼
  views/（画面係）が「保存して」と頼む
       │
       ▼
  state.js（管理人）が内容を整えて確定する
       │
       ├──▶ storage/local.js（保存係）がブラウザに書き込む
       │
       └──▶ 「変わったよ」と main.js（司令塔）に知らせる
                  │
                  ▼
            main.js が views/ に描き直させる
                  │
                  ▼
            画面が新しくなる
```

画面係が勝手に保存せず、保存係が勝手に画面を描かない。**誰が何をしたか、道筋が1本しかない**ので、不具合が起きたときに「どこで壊れたか」を順にたどれば必ず見つかる。逆に、どこからでもデータを触れる作りにすると、「いつの間にか値が変わっていた」を追う手段がなくなる。小さいアプリでも、この規律だけは最初から敷いてある。

## 第2章　`index.html` と `public/` — 骨組みと、そのまま配るもの

### 2.1 `index.html`（39行）— ほとんど空の骨組み

ブラウザが最初に受け取るファイル。開くと、まず head（頭書き）でこう宣言している。

| 行 | 意味 |
|---|---|
| `<meta charset="utf-8">` | 文字コードは UTF-8（日本語が化けない世界標準） |
| `<meta name="viewport" …>` | スマホでは画面幅に合わせて表示せよ |
| `<meta name="theme-color" …>` | ブラウザの枠の色。明るい設定と暗い設定で2色指定 |
| `<link rel="stylesheet" …>` | CSS を2枚読み込め（見た目の定義と、フォントの定義） |
| `<link rel="manifest" …>` | 「ホーム画面に追加できるアプリ」の設定ファイルの場所 |
| `<title>かけら</title>` | タブに出る名前 |

そして body（本体）は、驚くほど中身がない。

```html
<main id="main">
  <section id="today-view"></section>              ← 空
  <section id="outing-view" hidden></section>      ← 空。hidden=隠してある
  <section id="fragments-view" hidden></section>   ← 空
  <section id="about-view" hidden></section>       ← 空
</main>
<div id="onboarding-view"></div>                   ← 空
<div id="status" class="sr-only" role="status"></div>
<script type="module" src="./assets/app/main.js"></script>
```

**空の箱を4つ並べて、最後の1行で JavaScript を呼んでいるだけ**である。箱の中身は、呼ばれた JavaScript が状況に応じて入れる（第4章）。

なぜこうするのか。このアプリは「今日」「ひとつ」「かけら」「このアプリについて」の4画面を持つが、HTML ファイルは1枚しかない。画面の切り替えのたびにサーバーから新しいページをもらうのではなく、**同じページの中で箱の中身と表示/非表示を入れ替える**。こうすると切り替えが一瞬で済み、オフラインでも動く。この方式を SPA（シングルページアプリ）と呼ぶ。

細かいが意図のある部品が2つある。

- **`<a href="#main">本文へ</a>`**（先頭の1行）— 目には見えないが、キーボードだけで操作する人が Tab キーを押すと現れる「本文へ飛ぶ」ボタン。毎回ヘッダーを通過させないための配慮。
- **`<div id="status" role="status">`** — これも目に見えない。「記録を置きました」等の通知文をここに書き込むと、**画面読み上げソフトが自動で読み上げる**。目の見えない利用者への通知路として機能する。

### 2.2 `public/` — 加工せずそのまま配るもの

| ファイル | 何か |
|---|---|
| `favicon.svg` | タブに出る小さな絵。欠けた正方形（このアプリの象徴。第3章参照） |
| `icon-192.png` `icon-512.png` | ホーム画面に追加したときのアイコン。端末により使う大きさが違うので2つ |
| `site.webmanifest` | 「これはホーム画面に追加できるアプリです」とブラウザに伝える設定。名前・アイコン・背景色 |

これらは「材料」だが加工の必要がないので、ビルド時にそのまま完成品へコピーされる。

## 第3章　`styles.css` — 見た目の「定義だけ」を書く場所

81行しかない。しかも読むと、個々のボタンや見出しの見た目は**一切書いていない**。書いてあるのは**値の定義**だけである。

### 3.1 Tailwind CSS という道具

このアプリは Tailwind CSS という道具を使っている。仕組みはこう。

1. `styles.css` に「`sumi` という色は `#333c40` である」のように**名前と値の対応表**（`@theme` ブロック）を書く。
2. HTML や JavaScript の中で、部品に `class="text-sumi"`（文字色は sumi で）のように**名前で**指定する。
3. ビルド時に Tailwind が全ファイルを読み、**実際に使われている名前のぶんだけ** CSS を生成する。

利点は2つ。**色を変えたければ対応表の1か所を直すだけで全画面に効く。** そして、見た目の指定が部品のすぐ隣に書いてあるので、「このボタンの見た目はどこで決まっているのか」を探し回らなくて済む。

### 3.2 定義してある内容

**色（10色）。** 名前は日本の伝統色からとってある。名前自体が使い道を語る。

| 名前 | 意味 | 使い道 |
|---|---|---|
| `sushi`（鶯） | 地の色 | ページ全体の背景 |
| `men`（綿） | 紙の色 | カードや面 |
| `kei`（罫） | 罫線の色 | 枠線・下線 |
| `sumi`（墨） | 本文の色 | 記録の文字 |
| `nibi`（鈍） | 控えめな文字 | 説明・ラベル |
| `ai`（藍) | このアプリの主色 | ボタン、リンクの焦点 |
| `seiji`（青磁） | 月に一度だけの色 | 「ひとつ」（外出）だけに使う |
| `kin`（金) | 特別な一度だけの色 | 60日後の「読み返せます」だけに使う |
| `ai-usu` `seiji-usu` | 藍・青磁の薄い版 | 記録カードの背景 |

`seiji` と `kin` に注目してほしい。**色に「使ってよい場面」が決めてある。** 青磁は月に一度の外出、金は二か月に一度の開放のときにしか現れない。滅多に見ない色だからこそ、現れたときに特別だと分かる。

**書体（2つ）。** 記録の本文は明朝体（`mincho`）、操作部品はゴシック体（`gothic`）。**自分の書いた言葉と、アプリの都合の文字を、書体で区別する**ためである。

**文字サイズ・行間・字間・寸法。** `--spacing-touch: 2.75rem`（44px）は「指で押すものの最小寸法」。これより小さいボタンを作れないように名前で縛ってある。

**動き（3つ）。** 記録を置いたときにカードがそっと降りる `settle`、一言がゆっくり現れる `reveal`、「読み返せます」が息をするように明滅する `unlock`。いずれも0.4秒〜6秒の静かな動きだけ。派手な動きはこのアプリの性格に合わないので定義自体が存在しない。

**shard（欠けた角）。**

```css
@utility shard {
  clip-path: polygon(0 0, 100% 0, 100% calc(100% - 14px), calc(100% - 14px) 100%, 0 100%);
}
```

カードやボタンの**右下の角を斜めに欠けさせる**指定。このアプリの名前「かけら」を形にした、唯一の装飾である。favicon の「欠けた正方形」と同じ意匠。

**ダークモード。** ファイル末尾で、端末が「暗い表示」を選んでいる場合の色の対応表を丸ごと差し替えている。名前で指定する方式のおかげで、**差し替えるのは対応表だけ**で済み、各画面のコードは1文字も変わらない。

## 第4章　画面の切り替えと描画 — `main.js` と `views/`

### 4.1 `main.js`（156行）— 司令塔

アプリが起動して最初に動くファイル。仕事は「**いま、どの画面を出すべきか**」の判断と切り替えに徹していて、画面の中身は描かない。

**起動時にやること**（ファイル末尾の4行）。

```js
initialize();                                  // ① 保存されたデータを読み込む
history.replaceState(routeState("today"), ""); // ② 「いま今日の画面にいる」と履歴に記す
subscribe(render);                             // ③ 「データが変わったら描き直す」を予約
render();                                      // ④ 最初の描画
```

③が第1章で見た一方通行の要。**画面は「データが変わった通知」を受けて描き直されるだけ**で、自分から都合よく変わることはない。

**画面の切り替え（`navigate` と `goBack`）。** 「今月のひとつ」を押すと `navigate("outing")` が動き、(1) 全部の箱を隠して outing の箱だけ表示し、(2) その箱の中身を outing 担当に描かせ、(3) **ブラウザの履歴に「1ページ進んだ」と記録する**。この (3) のおかげで、スマホの「戻る」操作が期待どおり前の画面に戻る。1枚しか HTML がない SPA では、これをやらないと「戻る」でサイトから出て行ってしまう。

**日付をまたいだときの対応（`visibilitychange`）。** スマホでは、アプリを閉じずに何日も放置されることがある。23時に開いたまま寝て、翌朝また開くと、画面は昨日のままである。そこで「**画面が再び表示された瞬間に日付を確かめ、変わっていたら今日の画面に戻して描き直す**」処理が入っている。これがないと、翌日なのに昨日の記録が「今日のぶん」として表示され続ける。

**about 画面だけ後から取り寄せる。** `about.js` は起動時には読み込まず、初めて必要になった瞬間に取り寄せる（`await import(...)`）。「このアプリについて」は毎日開く画面ではないので、**毎日の起動を、滅多に使わない画面のぶんまで待たせない**ための工夫。

**`notify`（通知）。** 「記録を置きました」等の文を、第2章で見た読み上げ用の箱に書き込む。一度空にしてから書き直しているのは、同じ文を2回続けて入れると読み上げソフトが「変化なし」とみなして黙ってしまうため。

### 4.2 `views/` — 画面を描く係。共通の作法

5ファイルどれも同じ形をしている。

1. **受け取る**：描き込み先の箱、現在のデータ、通知係、画面遷移の関数
2. **組み立てる**：HTML の文字列を組み立てて箱に流し込む
3. **埋める**：ユーザーの書いた文字を、あとから安全な方法で埋め込む
4. **仕掛ける**：ボタンに「押されたらこうする」を仕掛ける

手順3が分かれているのには理由がある。ユーザーの入力を HTML に直接混ぜると、`<script>` のような文字列を書き込まれたときに**それがプログラムとして動いてしまう**（XSS という古典的な攻撃）。そこで骨組みは骨組みだけで作り、ユーザーの文字は `textContent`（文字としてしか扱われない安全な入れ方）で必ず後から入れる。この規律は全 view で一貫している。

### 4.3 `today.js`（203行）— 「今日」の画面

一番大きいファイル。理由は単純で、**この画面だけ状態が多い**からである。同じ「今日」でも、次の組み合わせで出すものが変わる。

| 状態 | 表示 |
|---|---|
| まだ書いていない | 入力欄（「心が動いたこと」＋任意の「済・人」） |
| 書いた直後 | 記録カード＋その日の一言＋（条件が揃えば）外出の「行った」ボタン |
| 書いた日に開き直した | 記録カード（一言は出さない） |
| 「書き直す」を押した | 入力欄に戻る（中身入り） |

意図の分かる作りをいくつか拾う。

- **「なし」ボタン** — 何もなかった日は、入力欄に「なし」と自動で入れて即保存する。「書けない日」を失敗にしないための、このアプリの中核機能。
- **一言は書いた直後だけ**（`justSaved`）— 366日ぶん用意された短い文（第5章）は、記録を置いた直後の一回しか出ない。開き直すと出ない。「書いたから読める」ではなく「書いた瞬間に立ち会った」だけの扱いにしてある。
- **自動フォーカスは1日1回**（`autofocusDate`）— 初めて開いたときは入力欄にカーソルを置くが、同じ日に2回目からは置かない。スマホでは、フォーカスのたびにキーボードがせり上がって画面を覆うため。
- **60日目の一度きりの知らせ**（`unlockNoticeVisible`）— 初めて書いた日から**ちょうど60日目**に記録を置いたときだけ、「読み返せます」という金色の一行が出る。`sessionStorage`（ブラウザを閉じると消える一時置き場）に「今日見せた」と記録して、同じ日に何度も出ないようにしてある。61日目以降は出ない。特別は一度だから特別である。
- **外出の「行った」** — 今月の外出が決めてあり、まだ行っていない場合だけ、記録カードの下に ◇ 印と「行った」ボタンが出る。押すと今日の日付が刻まれる。

### 4.4 `fragments.js`（70行）— 「かけら」の画面（一覧）

書いてきた記録が新しい順に並ぶ。ここに、このアプリで一番変わった仕様が実装されている。

```js
const unlocked = isUnlocked(state.started_on);            // 60日経ったか
const keys = unlocked ? allDateKeys(...) : recentDateKeys(); // 全部 or 直近7日
```

**初めて書いた日から60日間は、直近7日ぶんしか読み返せない。** 60日経つと全部が開き、「読み返せます」の金の文字と、全記録をテキストファイルで書き出すボタンが現れる。

なぜ隠すのか。書いてすぐ読み返せると、記録は「評価の対象」になる（今日のは短い、昨日より薄い……）。二か月置いてから読むと、ただの記録が「二か月前の自分の断片」になっている。**寝かせることが機能**なのである（REQUIREMENTS FR-4）。

書かなかった日は「—」と表示して、日付は詰めない。**空白の日も含めて並べる**が、埋めろとは言わない。外出した日には ◇ 印が添えられる。

### 4.5 `outing.js`（100行）— 「ひとつ」の画面（今月の外出）

月にひとつ、行ってみる場所を決める画面。決めてあれば青磁色のカードで表示し、なければ入力欄を出す。予定日は**決めなくてもよい**（日付欄に「決めなくてもかまいません」と出る）。画面下には常にこの文が出る。

> 今月、行ってみる場所をひとつ。
> 行く途中で気になる場所を見つけたら、そちらに変えてもかまいません。

達成を求めない、行き先の変更を最初から許す——この文言込みで要件（FR-3.6）である。月が変わると枠は新しくなり、**行かなかった月のことはどこにも表示されない**。実行率の集計も存在しない（NG-9：作らないと決めた機能）。

### 4.6 `about.js`（149行）— 「このアプリについて」

使い方の説明、記録の保存先の説明、控え（バックアップ）、やめるときの手続きが1画面にまとまっている。技術的に大事なのは後半の2つ。

**控え（バックアップ）。** 「控えを取る」を押すと、全記録が JSON ファイル（データを人にも機械にも読める形で書いたテキスト）としてダウンロードされる。サーバーがないこのアプリでは、**端末が壊れたら記録も消える**。その保険がこのファイルである。

**復元。** 控えのファイルを読み込ませると記録が戻る。ただし無条件には信じない。`validBackup` という関数が、**ファイルの中身が正しい形をしているか、日付は日付らしいか、文字数は上限内か**を全項目検査し、少しでもおかしければ「控えを読めませんでした」と断る。壊れたファイルで既存の記録を汚さないためである。また、復元は**いま端末にある記録を優先**して合成する（同じ日に両方の記録があれば端末側が勝つ）。復元操作で今日の記録が消える事故を防ぐ。

**使うのをやめる。** 全削除は3段階（申し出る → 控えを取ってから進むか選ぶ → 最終確認して消す）。取り返しのつかない操作の前に、控えという退路を必ず一度差し出す。

### 4.7 `onboarding.js`（16行）— はじめの言葉

初回だけ画面全体を覆って出る短い文。

> きれいだと思った。腹が立った。
> 消えてしまう前に、一日に一行、拾っておく。

説明でなく、このアプリの用途の**実物**を先に見せる。16行しかないのは、それ以上のことをしないから。あとから「はじめの言葉」として何度でも読み返せる。

### 4.8 `lib/dom.js`（28行）— 画面いじりの道具箱

「箱に流し込む」「探す」「文字を入れる」「押されたら教えて」「ファイルをダウンロードさせる」の5つの操作を短い名前にしただけの道具箱。中身はブラウザ標準機能の言い換えにすぎない。それでも作るのは、**画面を直接いじる箇所を数えられるようにする**ため。ブラウザ標準の書き方が将来変わっても、直すのはこの28行だけで済む。

## 第5章　データ — どこに、どんな形で、どう守って置くか

### 5.1 データの形

このアプリの全データは、たった1つの塊である。

```js
{
  version: 1,              // データの形の版番号（将来形を変えたとき用）
  started_on: "2026-06-01", // 初めて書いた日（60日の起点）
  onboarded: true,          // はじめの言葉を読み終えたか
  entries: {                // 日々の記録。「日付 → 記録」の表
    "2026-08-01": { feeling: "夕立のにおい", done: "", person: "", created_at: "…" }
  },
  outings: {                // 月ごとの外出。「月 → 外出」の表
    "2026-08": { goal: "海を見る", planned_on: null, went_on: null, created_at: "…" }
  }
}
```

表の鍵が**日付そのもの**（`"2026-08-01"`）であることに注目。「1日1件」というルールが、データの形そのもので強制されている。同じ日に2件目を書く方法が、構造上存在しない。

### 5.2 `state.js`（92行）— データの管理人

この塊を一手に持ち、**書き換えの窓口をすべて引き受ける**。窓口は6つしかない。

| 窓口 | すること |
|---|---|
| `saveEntry` | 今日の記録を保存。前後の空白を落とし、空なら拒否 |
| `saveOuting` | 外出の目的を保存 |
| `markOutingWent` | 外出に「行った日」を刻む。目的がない・すでに行った、なら何もしない |
| `finishOnboarding` | はじめの言葉を読み終えた印を付ける |
| `restoreBackup` | 控えから復元（端末側優先で合成） |
| `clearAll` | 全消去（まっさらな初期状態に戻す） |

どの窓口も、最後に必ず同じ関数 `commit` を通る。

```js
function commit(next) {
  value = next;                                    // ① 新しい塊に差し替え
  save(value);                                     // ② 保存係に書き込ませ
  subscribers.forEach((subscriber) => subscriber(value)); // ③ 予約者全員に知らせる
}
```

①で既存の塊を**書き換えるのではなく、丸ごと新しい塊に差し替えている**（`{ ...value, ... }` という書き方）。中身を部分的にいじる方式だと「いつ誰がどこを変えたか」が追えなくなるが、差し替え方式なら「commit の瞬間に全部変わる」の一点に絞れる。③が第1章の一方通行の通知で、これを受けて main.js が画面を描き直す。

### 5.3 `storage/local.js`（39行）— 保存係と localStorage

実際の保存先は **localStorage**。ブラウザが各サイトに用意している小さな物置で、次の性質を持つ。

- サイトごとに別。他のサイトからは読めない
- ブラウザを閉じても消えない
- **その端末のそのブラウザにしかない**。他の端末とは共有されない
- ユーザーが「閲覧データを削除」すると消える

最後の2点がこのアプリの弱点であり、だからこそ「控え」（4.6節）がある。この事情は隠さず、アプリ内の「記録の保存先」にも明記してある。

保存係のコードで大事なのは、読み込み時の疑い深さである。

```js
export function load() {
  try {
    const stored = localStorage.getItem(KEY);
    return stored ? normalize(JSON.parse(stored)) : emptyState();
  } catch {
    return emptyState();   // 壊れていたら、まっさらな状態で始める
  }
}
```

保存されていたデータが壊れていても（手でいじられた、別バージョンだった、読み込み自体が禁止されていた）、**アプリは絶対に起動に失敗しない**。`normalize` が形を検査して直し、直せなければ初期状態で開く。日記帳が読めないからといって、今日書けないのはおかしい、という判断である。

### 5.4 `storage/index.js` — たった1行のファイル

```js
export { load, save, clearAll, empty } from "./local.js";
```

「保存係は `local.js` です」という**掲示**だけのファイル。管理人（state.js）はこの掲示を見て保存係を呼ぶので、将来サーバー保存に切り替えるときは、**この1行を書き換えるだけ**で、他のファイルは1文字も変わらない。差し替えの継ぎ目をあらかじめ1か所に作ってある。

### 5.5 `lib/date.js`（70行）— 日付の計算をすべて引き受ける

日付の計算は、プログラミングで最も事故の多い領域である（月末、うるう年、時差、夏時間）。そこで**日付に触る計算は全部このファイルに集め、他では一切計算しない**と決めてある。

- `dateKey()` — 今日を `"2026-08-01"` の形にする。**端末の時計の日付**を使う。深夜0時に日付が替わるのは、ユーザーの生活感覚と同じにするため
- `fromDateKey()` — 文字列を日付に戻す。このとき**昼の12時**として解釈する。0時ちょうどにすると、夏時間のある地域で日付が1日ずれる事故が知られているため、一番安全な昼に寄せてある
- `isUnlocked()` — 初日から60日経ったか。「読み返せます」の判定はこの1か所
- `monthDayIndex()` — 「8月1日は1年の何日目か」を、うるう年を**含む**366日の表で引く。今日の一言（次節）の割り当てに使う

### 5.6 `data/lines.json` — 今日の一言 366件

```json
{ "01-01": "年のはじめの空は白っぽい", "08-01": "夕立のあと、道の匂いが変わる" }
```

記録を置いた直後に一度だけ表示される短い文が、うるう日を含む366日ぶん。**日付だけで決まり、何を書いたか・何日続けたかでは変わらない。** 「よく続けましたね」の類を言わせないためである（FR-8）。文はすべて、字数12〜24字・句点なし・二人称なし・評価語なし、という規則で書かれている。

このファイル、実は完成品には**そのままの形では入らない**。理由と行き先は次章で。

## 第6章　`web/` の設定ファイル — 部品の取り寄せ

JavaScript をブラウザの外（手元のパソコン）で動かす土台が **Node.js**、部品（他人の作ったプログラム）を取り寄せる道具が **npm** である。このアプリでは、ビルド（第7章）にだけこれらを使う。

| ファイル | 何か |
|---|---|
| `package.json` | このプロジェクトの名札。使う部品の一覧と、`npm run build` という作業名の定義 |
| `package-lock.json` | 取り寄せた部品の**正確な版**の記録。誰のパソコンでも寸分違わぬ同じ部品が揃う。npm が書くので手では触らない |
| `.nvmrc` | Node.js 自体のバージョン指定 |
| `node_modules/` | 取り寄せた部品の実体。`npm ci` で組み上がる。**Git に入れない**（lock ファイルから何度でも再現できるから） |

`package.json` を開くと、部品は4つしかない。フォント2種（Zen Old Mincho、Zen Kaku Gothic New）、Tailwind CSS とその命令行道具。しかも全部 `devDependencies`（**開発時だけ使う部品**）の欄にある。つまり——**完成品のアプリは、他人のプログラムを1行も含んでいない**。ブラウザで動くコードはすべてこのリポジトリに書かれた約1,000行だけである。部品は増やすほど、更新・脆弱性・容量の面倒を抱え込む。このアプリの規模なら、抱えない方が安い。

## 第7章　`scripts/build.js`（159行）— 組み立て工場

`npm run build` と打つと動く。材料（`src/`）から完成品（`dist/`）を**毎回ゼロから**作り直す（まず dist を全消去してから始める）。工程は6つ。

### 工程1〜2　コピー

`index.html` と `app/` の JavaScript と `public/` の中身を、完成品の配置にコピーする。

### 工程3　フォントの組み立て

日本語フォントは巨大である（1書体まとめると1.8MB）。全部を配ると、初めて開いた人が使いもしない何千字ぶんを受け取ることになる。そこで取り寄せたフォント部品は、**文字の範囲ごとに約240個の小さなファイルに分割**されたものを使う。

ビルドはフォント部品の中から「どのファイルがどの文字を担当するか」の対応表（`@font-face` の並び）を取り出し、配布用の書き方に直して `fonts.css` を作り、参照されているフォントファイルだけを `dist/fonts/` へコピーする。ブラウザはこの表を読み、**画面に実際に出た文字が入っているファイルだけ**を取りに来る。実測では、初回に落ちるのは十数ファイル・約200KB。珍しい漢字を書けばその瞬間に追加で落ちてくるので、表示できない文字はない。

古い形式（woff）への言及が残っていたらビルドを**失敗させる**検査も入っている。中途半端な出力を黙って配らないためである。

### 工程4　今日の一言を JavaScript に変換する（このビルドの一番の変わり種）

`lines.json` はそのまま配らず、`lines.js` という JavaScript ファイルに変換する。理由は2つある。

**理由1：セキュリティ設定との両立。** このアプリの配信には「**ブラウザからの外部通信を全面禁止**」というセキュリティ設定を付けてある（第8章の `connect-src 'none'`）。記録を外に送らないことを、アプリの善意でなくブラウザの強制力で保証するためである。ところがこの設定は、**自分のサーバーの JSON を読みに行くことすら禁止**してしまう。そこでデータの取り寄せをやめ、プログラムの一部（`import` で読み込める形）に変えて同梱する。

**理由2：小さくなる。** 変換のついでに、366本の文を圧縮している。仕組みは「**よく出る文字の並びに、短い符号を割り当てる**」——たとえば「の匂い」が何度も出てくるなら、それを1文字ぶんの符号に置き換え、置き換え表を添えて配る。受け取った側は表を逆に引いて元に戻す。この方式（バイトペア符号化）は、実は ChatGPT などの AI が文章を扱うときに使うのと同じ考え方である。復元コードは3行ほどで、変換後のファイルは元の JSON より小さい。

### 工程5　JavaScript の軽量化（ミニファイ）

コメント（人間向けのメモ）と余分な空白・改行を取り除く。プログラムの意味は変えず、ファイルを小さくして転送を速くする。この処理も既製品を使わず、50行ほどで自作してある——引用符の中は触らない、単語同士がくっつかないよう必要な空白だけ残す、という規則だけの素朴な作りだが、この規模のアプリにはそれで足りる。

### 工程6　CSS の生成と、超過の検査

Tailwind（第3章）を動かして、実際に使われている名前のぶんだけの CSS を生成する。そして最後に一風変わった検査がある。

```js
if (Buffer.byteLength(tailwindCss) > 20 * 1024) {
  throw new Error(`Tailwind CSS exceeds 20 KB: ...`);
}
```

**CSS が20KBを超えたらビルドを失敗させる。** 見た目の指定は放っておくと際限なく膨らむ。「このアプリの見た目は20KBで表現しきれる規模を保つ」という設計上の約束を、人間の注意力ではなく機械の検査にしてある。

### 完成品 `dist/` の姿

```
dist/
├── index.html            骨組み
├── assets/
│   ├── styles.css        見た目（20KB以下を保証）
│   ├── fonts.css         フォントの対応表
│   └── app/              頭脳（軽量化済み。lines.js を含む）
├── fonts/                フォント本体（約240ファイル・4.5MB）
├── favicon.svg / icon-*.png / site.webmanifest
```

**ここを直接編集してはいけない。** 次のビルドで跡形もなく消える。直すのは必ず `src/`。また Git にも入れない——材料と工場があれば、いつでも同じものが作れるからである。

## 第8章　配信 — AWS と自動デプロイ

### 8.1 構成

```
利用者のブラウザ ⇄ CloudFront（世界中にある配達拠点） ⇄ S3（ファイルの倉庫・非公開）
```

- **S3** — dist/ の中身を置く倉庫。**直接は誰にも読ませない**設定にしてある
- **CloudFront** — 利用者に近い拠点にファイルの写し（キャッシュ）を置いて速く配る配達網。HTTPS（通信の暗号化）もここが受け持つ。倉庫を読めるのは CloudFront だけ

### 8.2 `infra/` — AWS への申請書類（4枚）

これらは配信されるファイルではなく、**AWS 側の設定を作るための書類**である。

| ファイル | 内容 | なぜ |
|---|---|---|
| `s3/bucket-policy.json` | 「この倉庫を読めるのは、うちの CloudFront だけ」 | 倉庫の直接公開は、設定ミス一つで全ファイル流出につながる定番事故。入口を1つにする |
| `cloudfront/response-headers-policy.json` | 配信するファイル全部に付ける約束書き（セキュリティヘッダー）。**外部通信の全面禁止**（`connect-src 'none'`）、他サイトへの埋め込み禁止、HTTPS 強制など | 「記録を外に送らない」をブラウザに強制させる。仮にコードに悪意ある行が紛れ込んでも、通信自体をブラウザが遮断する |
| `iam/deploy-role-trust.json` | 「デプロイを許すのは、この GitHub リポジトリの main ブランチだけ」 | 誰でも上書きできる倉庫にしないため |
| `iam/deploy-role-policy.json` | デプロイ時にできることの一覧（この倉庫への書き込みと、キャッシュの掃除**だけ**） | 万一デプロイの鍵が漏れても、できることがこの2つしかない |

全体を貫くのは**最小権限**という考え方——「必要なことだけを、必要な相手にだけ許す」。

### 8.3 `.github/workflows/deploy-web.yml` — 自動デプロイ

GitHub の main ブランチに変更を push すると、GitHub のサーバーが自動でこの手順書を実行する。

1. リポジトリを取得し、指定版の Node.js を用意する
2. `npm ci` で部品を取り寄せ、`npm run build` で組み立てる
3. dist/ を S3 へ同期する。ただし**ファイルの種類で扱いを変える**：
   - フォントや JS など → 「1時間は写しを使ってよい」
   - `index.html` → 「**毎回確かめよ**」（ここが古いと、更新したのに古いアプリが開き続けるため。入口だけは常に最新を保証する）
   - アイコン → 「1日使ってよい」（滅多に変わらないので長め）
4. CloudFront の各拠点に残る古い写しを掃除する

注目すべきは、**AWS のパスワードや鍵をどこにも保存していない**こと。GitHub と AWS が互いに身元を確かめ合う仕組み（OIDC）で、実行のたびに数分だけ有効な通行証を発行してもらう。長生きする鍵は、いつか漏れる。だから最初から作らない。

なお `paths:` の指定により、`web/` 以下か手順書自身が変わったときしか動かない。docs だけ直した push で配信作業をやり直さないためである。

## 第10章　通し稽古 — ある一日のアプリの動き

ここまでの全部品が実際にどう連携するか、一日の流れで追う。

**朝、ホーム画面のアイコンを押す。**
ブラウザが CloudFront から `index.html` を受け取る（入口は「毎回確かめよ」なので必ず最新。中身が前回と同じなら写しで即座に済む）。HTML が CSS 2枚と `main.js` を呼ぶ。`main.js` が動き出し、`state.js` の `initialize()` が localStorage から記録の塊を読み込む。壊れていても初期状態で立ち上がる。今日の日付をつくり（`date.js`）、今日の記録はまだ無いので、`today.js` が入力欄を描く。カーソルが「心が動いたこと」に置かれる（今日はまだ初回なので）。

**「セミが鳴きやんだ瞬間、静かすぎた」と書いて「記録する」を押す。**
`today.js` は自分で保存せず、`state.js` の `saveEntry` を呼ぶ。管理人は空白を整え、新しい塊を作って `commit`——保存係が localStorage に書き込み、予約していた `main.js` に「変わった」と通知が飛び、画面が描き直される。記録カードが `settle` の動きでそっと降り、8月のその日の一言が `reveal` でゆっくり現れる。読み上げソフトには「記録を置きました」が流れる。

**下の「今月のひとつ」を押す。**
`navigate("outing")` が動く。today の箱が隠れ、outing の箱が現れ、履歴に1ページ積まれる。今月はまだ決めていないので入力欄が出る。「海を見る」と書いて決める。青磁色のカードに載る。スマホの「戻る」で今日に帰る（履歴に積んであったから戻れる）。

**夕方、海へは行かず、途中の古い喫茶店に入った。**
それでいい。画面の文にそう書いてある。帰って「今日」を開くと、記録カードの下に「◇ 海を見る　行った」が出ている。押す。`markOutingWent` が今日の日付を刻む。目的地と違う場所に行ったことは、誰にも咎められない——咎める機能が存在しないからである。

**夜、もう一度開く。**
記録カードは出るが、一言はもう出ない（`justSaved` は開き直しでは立たない）。「書き直す」で文面を直せるのは今日のうちだけ。日付が変われば、`visibilitychange` の見張りが新しい「今日」を用意し、昨日のことは確定する。

これが全部である。サーバーには今日一日、**ファイルをくれという要求以外、何ひとつ送られていない**。

## 第11章　まとめ — 結局、何をどこに上げるのか

```
① 材料       web/src/  web/public/                → 上げない
③ 道具・書類  web/scripts/ docs/ infra/ .github/  → 上げない
② 完成品     web/dist/                            → ★ここだけ上げる
```

手動でやるなら、必ずこの順。

```bash
cd web
npm ci            # 部品を取り寄せる（lock ファイルどおりの正確な版で）
npm run build     # dist/ をゼロから作り直す
aws s3 sync dist/ s3://<バケット名>/ --delete
```

`npm run build` を飛ばして同期すると、**前回のビルド結果**が上がる（か、dist が無くて何も上がらない）。普段は main に push すれば第8章の自動デプロイが同じことをやってくれるので、手で打つのは非常時だけである。

最後に、この設計全体を貫く考え方を3行で。

1. **流れは一方通行に1本だけ**（操作 → 管理人 → 保存 → 通知 → 描画）。追えない変化を作らない。
2. **約束は人の注意力でなく仕組みで守る**（通信禁止はブラウザに強制させる。CSS の肥大はビルドが拒む。1日1件はデータの形が拒む）。
3. **持たないことが最強の保護**（サーバーに記録を持たない。外部部品を完成品に持たない。長生きする鍵を持たない。作らない機能は仕様書に書いて作らない）。
