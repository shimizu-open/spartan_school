## 0. この課題の目的（実装前に必ず読むこと）

これは「かっこいいサイトを1本納品する」課題ではない。目的は次の3つ。

1. Webページのレイアウトには「よくある型」が複数あり、それぞれ使いどころが違うことを、
   **同一コンテンツを型だけ変えて実装する**ことで体感する。
2. 選んだ型について「なぜこの型か」「**なぜ他の型を選ばなかったか**」を
   自分の言葉で説明できるようになる。
3. 半年後に本人が読み返して思い出せる**学習ドキュメントを残す**。

したがって設計方針は次の3点。

> **(A) `patterns/` 配下の5本は、本文の中身を完全に同一にし、
> 違いを「タグの構造」と「CSSのレイアウト指定」だけに限定すること。**
>
> **(B) 解説はすべて成果物のファイル内に書くこと。
> 実装者の頭の中や、チャットの説明に留めてはならない。**
>
> **(C) `museum/` は、ページごとに意図的に異なる型を使い分けること。
> 「1サイトの中で型を弾き分ける」実例にするため。**

### 読者像（超重要）

このドキュメントを読むのは、**「自分が何を知らないかも分かっていない」段階の初学者**である。
解説を書くときは常に次を守ること。

- **専門用語は初出時に必ず一言で説明する。**
  ✅「`position: sticky`（スクロールしても画面に貼り付いて付いてくる指定）」
  ❌「sticky で追従させます」
- **「なぜそうするのか」を必ず書く。** 手順だけ書いても学習にならない。
- **失敗例・弱点を必ず書く。** 「いつ使うか」より「**いつ使ってはいけないか**」の方が価値がある。
- **カタカナ語には言い換えを添える。** 「聖杯レイアウト（Holy Grail、3カラム）」
- 曖昧な断定回避をしない。「〜な場合もあります」ではなく「メニューが7個以下ならヘッダーナビ」

## 2. 共通の技術要件（全ページ）

### 2.1 必須

| 項目 | 要件 |
|---|---|
| DOCTYPE | `<!DOCTYPE html>` のみ |
| 言語 | `<html lang="ja">` |
| 文字コード | `<meta charset="UTF-8">` を head の先頭に |
| ビューポート | `<meta name="viewport" content="width=device-width, initial-scale=1.0">` |
| タイトル | ページごとに固有の `<title>` |
| 見出し | `h1` は各ページ1つ。`h1→h2→h3` を飛ばさない |
| 画像 | `alt` 必須。装飾目的の画像は `alt=""` |
| インデント | 2スペース |

### 2.2 禁止事項（「古い書き方」の排除）

- レイアウト目的の `<table>`（**データの表としての `<table>` は正しい用法なので可**）
- レイアウト目的の `float`
- `<center>` `<font>` `<b>` `<i>` などの非推奨タグ（強調は `<strong>` / `<em>`）
- `style="..."` によるインラインスタイル
- `<div class="header">` のような、セマンティックタグで表現できる箇所での `div` 濫用
- jQuery、その他あらゆる外部ライブラリ
- `<br>` による余白調整（余白は CSS の `margin` で取る）

### 2.3 使うべきセマンティックタグ

`header` / `nav` / `main` / `aside` / `section` / `article` / `footer` / `dl,dt,dd` /
`figure,figcaption` / `time` / `ol,ul`

`div` は「意味はないが装飾のためにまとめたい」場合にのみ使用可。

### 2.4 アクセシビリティ

- `<nav>` が複数ある場合は `aria-label` で区別する
- 開閉ボタンは `<button>` を使う（`<a href="#">` や `<div onclick>` は不可）
- 開閉ボタンには `aria-expanded` と `aria-controls` を付け、JSで状態を更新する
- キーボードだけで全リンク・全ボタンを操作できること
- `:focus-visible` のフォーカスリングを消さない（見やすく作り替えるのは可）
- `@media (prefers-reduced-motion: reduce)` でアニメーションを無効化する
- 本文と背景のコントラスト比 4.5:1 以上
- 各ページ先頭に「本文へスキップ」リンクを置く（普段は見えず、Tab で現れる）

## 3. `patterns/` — 5つの型（比較用）

### 3.1 共通ルール

- 中身は `CONTENT.md` の **§2 人物名鑑の冒頭3人分**（ホームズ・ワトスン・ハドスン夫人）を使う。
  5本すべて**一字一句同一**のテキストにすること。
- `shared.css` は **色を付けない**。背景白・文字黒・行間・余白・フォントのみ。
  レイアウト領域が分かるよう、`header/main/aside/nav/footer` に薄いグレーの境界線だけ引く。
- 各領域の左上に、CSS の `::before` でタグ名ラベル（`<header>` `<main>` `<aside>` `<footer>`）を
  小さく表示する。**どのタグがどこに対応しているかを目で見て分からせるため**。
- `layout.css` には**そのパターンのレイアウトに必要な指定だけ**を書く。
  「この型は10〜20行で表現できる」と分かる状態にする。
- **画像は使わない**（構造の学習に集中させる）。

### 3.2 各ページに埋め込む解説ブロック（必須）

各ページの `<main>` の直前に置く。`<details>` で畳まず、**常に開いた状態**で表示すること。

```html
<aside class="pattern-note" aria-label="このパターンの解説">
  <p class="pattern-note__label">レイアウトパターン 01</p>
  <h2>1カラム（シングルカラム）</h2>

  <pre class="pattern-note__diagram" aria-hidden="true">
（アスキー図。§4の各定義を参照）
  </pre>

  <h3>ひとことで言うと</h3>
  <h3>なぜこの形にするのか</h3>
  <h3>向いている場面</h3>
  <h3>向かない場面・弱点</h3>
  <h3>初心者がやりがちな失敗</h3>
  <h3>この型を作るCSSの核心</h3>
  <h3>資料館ではどう使ったか</h3>   ← museum/ のどのページで使った／使わなかったか＋理由

  <p class="pattern-note__link">
    <a href="../../GUIDE.md">→ もっと詳しい解説（GUIDE.md）</a>
    ／ <a href="../../index.html">← パターン一覧に戻る</a>
  </p>
</aside>
```

§4 は**要点のメモ**である。そのまま貼るのではなく、§0「読者像」の方針で
**初学者に伝わる文章に展開して書くこと**。

### 3.3 レスポンシブの共通方針

ブレークポイントは **768px** のみ。それ以下では原則すべて1カラムに縦積みする。
縦積み時の順序は各パターン定義に従う（`order` プロパティを使う）。

## 4. 各パターンの定義

### パターン01：1カラム（シングルカラム）

```
┌─────────────┐
│   header    │
├─────────────┤
│    main     │
├─────────────┤
│   footer    │
└─────────────┘
```

**レイアウト要件**
- 中央寄せ。`main` の最大幅 `720px`、`margin-inline: auto`
- 本文の1行文字数を `max-width: 65ch` 程度に抑える
- **Flexbox も Grid も使わないこと。** 不要な道具は使わない、というのも学習ポイント

**解説の要点**
- ひとことで：上から下に積むだけの、最も単純な型
- なぜ：読ませることが目的なら、横にあるものは全部ノイズになる
- 向く：ブログ記事、ニュース記事、LP、読み物
- 向かない：目次を常に見せたいページ。長文で現在地を見失う
- 失敗：`main` に最大幅を指定し忘れ、大画面で1行が100文字を超えて激烈に読みにくくなる。
  **人が快適に読める行長は40〜75文字**。だから `max-width: 65ch`（`ch` は「0の字幅」の単位）
- CSSの核心：`max-width` と `margin-inline: auto` の2行だけ。`auto` は「左右の余白を均等に」
- 豆知識：スマホでは結局どの型も1カラムに崩れる。**1カラムだけは崩す必要がない＝一番ラク**
- 資料館では：**年表ページ**の骨格に採用。時系列は縦一本が最も読みやすく、
  横に何か置くと読む流れを邪魔するから

---

### パターン02：2カラム（サイドバー付き）

```
┌─────────────┐
│   header    │
├───────┬─────┤
│ main  │aside│
├───────┴─────┤
│   footer    │
└─────────────┘
```

**レイアウト要件**
- `.layout` を **Flexbox** で横並びにする（`display: flex`）
- `main` は `flex: 1` ＋ `min-width: 0`
- `aside` は `flex: 0 0 240px`（伸びない・縮まない）
- `aside` は `position: sticky` でスクロール追従させる
- 768px 以下：`flex-direction: column`。`aside` は `order: 2` で本文の**下**へ

**解説の要点**
- ひとことで：本文の横に、目次や絞り込みの細い列を添える型
- なぜ：「本文を見ながら常に触れるようにしたい操作／情報」の置き場ができる
- 向く：技術ドキュメント、長い解説記事、商品一覧の絞り込み
- 向かない：スマホ利用が大半のページ（サイドバーが下に落ちて価値が半減する）
- 失敗①：`main` に `min-width: 0` を付け忘れる。Flexbox の子要素には
  **「中身より小さくならない」という初期設定**があるため、長いURLや広い表があると
  はみ出して崩れる。この1行はおまじないではなく、その初期設定の解除である
- 失敗②：サイドバーを左に置く。**読み物なら右が基本**。人は左上から読むので、
  本文を先に目に入れたいから。左に置くのは「ナビが主役」のアプリ系
- CSSの核心：`display: flex` ＋ 本文に `flex: 1`（余りを全部もらう）
  ＋ サイドバーに `flex: 0 0 240px`（伸びない・縮まない・240px）
- 資料館では：**作品総覧ページ**に採用。左に絞り込み、右に作品カード。ECサイトと同じ構造

### パターン03：折りたたみサイドパネル

```
開いた状態              閉じた状態
┌─────────────┐        ┌─────────────┐
│   header    │        │   header    │
├─────┬───────┤        ├──┬──────────┤
│ nav │ main  │        │▪ │  main    │
├─────┴───────┤        ├──┴──────────┤
│   footer    │        │   footer    │
└─────────────┘        └─────────────┘
```

**レイアウト要件**
- Flexbox。`aside` は**左**に配置（パターン02との対比）
- 開閉状態は `aside` の `data-open="true" / "false"` 属性で表現する
- 開：幅 `240px` ／ 閉：幅 `56px`（アイコンだけ残す）
- 幅の変化に `transition` を掛けてスッと動かす
- 閉じている時、アイコンにマウスを載せると項目名が出ること（`title` 属性でよい）
- 768px 以下：`aside` を `position: fixed` のドロワーにし、
  画面左外（`transform: translateX(-100%)`）から滑り込ませる。
  開いている間は背後に半透明のオーバーレイを敷き、クリックで閉じる

**JS要件（`sidebar.js`）**
- `#sidebarToggle` のクリックで `data-open` を反転
- `aria-expanded` を同時に更新
- Esc キーで閉じる（ドロワー表示時）
- **JSから `element.style` を直接いじらないこと。** JSは属性・クラスの切り替えのみ。
  見た目の変化はCSSの責務。コード内にその理由をコメントで明記すること

**解説の要点**
- ひとことで：サイドバーをボタンで開閉できるようにした型
- なぜ：情報を見たいときだけ開き、本文に集中したいときは畳んで幅を譲れる
- 向く：管理画面、ダッシュボード、項目数の多いナビゲーション
- 向かない：ページ数が少なく常時表示で足りるサイト（開閉は操作コストになる）
- 失敗①：閉じてアイコンだけになると**何のアイコンか分からなくなる**。ホバーで名前を出す配慮が必須
- 失敗②：`<div onclick="...">` で開閉ボタンを作る。`<div>` はキーボードで
  フォーカスできないため、**マウスが使えない人が永久に開けない**。`<button>` を使う
- 失敗③：JSで `sidebar.style.width = "56px"` と直接書く。見た目の定義がCSSとJSに散らばり、
  後から変更するとき両方を直す羽目になる
- CSSの核心：`data-open="false"` の時の見た目をCSS側に書いておき、JSは属性を書き換えるだけ。
  **「状態はJS、見た目はCSS」の役割分担**
- 資料館では：**採用していない**。全5ページしかなく、開閉の操作コストが得られる幅より大きいため。
  **使わない判断をしたこと自体が理解の証拠**である

### パターン04：聖杯レイアウト（Holy Grail、3カラム）

```
┌───────────────┐
│    header     │
├────┬─────┬────┤
│nav │main │side│
├────┴─────┴────┤
│    footer     │
└───────────────┘
```

**レイアウト要件**
- **CSS Grid** で実装する（Flexbox では書かないこと。パターン02との対比が目的）
  ```css
  grid-template-columns: 200px 1fr 200px;
  ```
- `main` が HTML 上も中央に来るように書く（`order` による DOM 順の入れ替えをしない）
- 768px 以下：1カラムに縦積み。順序は `main` → `nav` → `aside`

**解説の要点**
- ひとことで：本文を左右のサイドバーで挟む3カラム
- なぜ「聖杯」と呼ばれるか：`float` しかなかった時代、
  「本文をHTMLの先に書きつつ、画面では真ん中に置く」の両立が至難だった。
  誰も到達できない伝説の杯、という皮肉な呼び名。**今は CSS Grid で1行**
- 向く：ニュースポータル、情報量の多いサイト
- 向かない：中身が少ないサイト。空の列が本文を狭めるだけになる。**個人サイトではまず不要**
- 失敗：埋めるものが無いのに3カラムにする。**カラムは増やすほど本文が狭くなる**
- CSSの核心：`display: grid` ＋ `grid-template-columns: 200px 1fr 200px`。
  `1fr` は「余った幅を全部」の意味。左右を固定幅にして、中央に残り全部を渡している
- 位置づけ：今や歴史的な型。作る価値はあるが、それは**なぜ簡単になったかを知るため**
- 資料館では：**採用していない**。右カラムに置くほどの情報量がなく、
  空のカラムは本文を狭めるだけになるため

**HTMLコメントとして残すこと**
> この型が「聖杯」と呼ばれた理由：float しかなかった時代は、
> 中央カラムをHTML上で先に書きつつ画面上は中央に置く、という両立が困難だった。
> Grid では grid-template-columns の1行で解決する。

### パターン05：ヘッダーナビ ＋ ハンバーガーメニュー

```
広い画面                        狭い画面
┌──────────────────┐          ┌──────────┐
│ LOGO   A  B  C   │          │ LOGO  ☰  │
├──────────────────┤          ├──────────┤
│      main        │          │  main    │
└──────────────────┘          └──────────┘
```

**レイアウト要件**
- 骨格自体は1カラム（**この型は層が違う＝ナビの型であり骨格の型ではない**ことを解説で明示する）
- `header` は Flexbox でロゴ左・ナビ右（`justify-content: space-between`）
- `header` は `position: sticky; top: 0` で上に貼り付く
- `html { scroll-padding-top: ヘッダー高さ }` を入れる
  （入れないとページ内リンクで飛んだ先の見出しがヘッダーの下に隠れる。理由をコメントに書く）
- 640px 以下：ナビを畳み、`☰ MENU` ボタンを表示。
  ナビは画面上から滑り降りるパネルにする（`transform: translateY(-100%)` → `0`）
- `☰` の3本線が `✕` に変形するアニメーション（CSS の `transform` のみで実現）
- ボタンには `☰` だけでなく **`MENU` の文字を添える**（アイコンだけでは意味が伝わらないため）

**JS要件（`nav.js`）**
- クリックで `header` に `is-open` クラスをトグル
- `aria-expanded` / `aria-label` を更新
- メニュー内リンクのクリックで自動的に閉じる
- Esc キーで閉じ、フォーカスをボタンに戻す
- `element.style` への直接代入は禁止（パターン03と同じ原則）

**解説の要点**
- ひとことで：上部バーにロゴとメニューを並べ、狭い画面では ☰ に畳む型
- **重要**：これは「骨格の型」ではなく「**ナビゲーションの型**」。
  1カラムにも2カラムにも聖杯にも重ねられる。課題のリストで横並びに書かれているが、層が違う
- なぜ：メニューは画面上部にあると期待されている。期待に逆らわないのが親切な設計
- 目安：メニューが**7個以下**ならこの型で足りる。それ以上なら折りたたみサイドバーを検討
- 向く：ほぼすべてのWebサイト。**迷ったらこれ**
- 失敗①：`☰` だけ置く。アイコンの意味が伝わらない人が一定数いる。文字を添える
- 失敗②：`scroll-padding-top` を忘れ、目次リンクで飛ぶと見出しが固定ヘッダーに隠れる
- 失敗③：メニューを開いたまま閉じられなくなる。Esc とリンククリック時の自動クローズを用意する
- CSSの核心：`position: sticky; top: 0` の2行で「上に貼り付く」が実現する。
  昔は `position: fixed` ＋ 本文に余白を足す手作業が必要だった
- 資料館では：**全5ページ共通のナビとして採用**。ページ数が5なので上部バーに全部収まる

### §7「CSSの3つの道具」に必ず書くこと

初学者が最も混乱するのがここなので、独立した章で丁寧に扱う。

| 道具 | ひとことで | 使う場面 | 覚え方 |
|---|---|---|---|
| 通常フロー（何もしない） | ブロック要素は上から下に積まれる | 1カラム、文章 | **デフォルトで十分なら何も書かない** |
| Flexbox | **一列**に並べて余りを配り合う | ヘッダーの左右振り分け、2カラム、ボタンの横並び | 「1本の線に並べる」 |
| Grid | **格子**に配置する | 3カラム、カード一覧、ダッシュボード | 「方眼紙に置く」 |

- **迷ったときの判断基準**：「1方向に並べたい」なら Flexbox、「縦横どちらも制御したい」なら Grid
- 2カラムはどちらでも書ける。本教材ではパターン02を Flexbox、パターン04を Grid で書き、
  **同じ多カラムを両方の道具で書き比べる**構成にしてある
- `repeat(auto-fill, minmax(220px, 1fr))` の読み下し：
  「220px を下限として、入るだけの列を自動で作り、余りは均等に分配する」
  → **メディアクエリを1行も書かずに列数が可変になる**。今風の書き方の代表格

### §6「選び方のフローチャート」

テキストの分岐図（コードブロック）で書く。例：

```

├─ YES → 常に見せたい目次や操作がある？
│         ├─ NO  → 【1カラム】
│         └─ YES → 【2カラム】
└─ NO  → 一覧から選んで詳細を見る動きが中心？
          ├─ YES → 【マスター＋ディテール】

                    ├─ YES → 【ダッシュボード】
                    └─ NO  → 【1カラム＋ヒーロー】
```

### §8「資料館での実際の選択」

## 7. `museum/` — ベイカー街資料館（本命）

### 7.1 コンテンツ

`CONTENT.md` を**そのまま**使用する。テキストの創作・改変・追加は**禁止**。
特に `CONTENT.md` §6「事実確認メモ」の禁止事項を厳守すること。

### 7.2 デザイン方針

19世紀末ロンドンのガス灯。ダークテーマ。**資料館らしい静けさ**。装飾過多にしない。

**デザイントークン（`base.css` の `:root` に定義）**

| 変数名 | 値 | 用途 |
|---|---|---|
| `--bg` | `#0d0f12` | 背景 |
| `--bg-elev` | `#14171c` | カードなど一段浮いた面 |
| `--line` | `#262b33` | 罫線 |
| `--text` | `#e6e4df` | 本文 |
| `--muted` | `#8c8f96` | 補助テキスト |
| `--accent` | `#c8a45c` | 真鍮／ガス灯のゴールド。アクセント |
| `--header-h` | `64px` | ヘッダー高さ |
| `--max-w` | `1200px` | コンテンツ最大幅 |

- 見出しとロゴは**セリフ体**、本文は**サンセリフ体**（ともにシステムフォント。Webフォント禁止）
- アクセント色は「差し色」。面で塗らず、線・小さな文字・ホバー時にのみ使う

### 7.3 全ページ共通（`base.css` / `nav.js`）

- ヘッダー：`position: sticky; top: 0`、`backdrop-filter: blur()`、Flexbox でロゴ左・ナビ右

- フッター：`CONTENT.md` §0 の文言。パブリックドメインの但し書きを必ず載せる
- 「本文へスキップ」リンク

### 7.4 ページ別の要件

#### ① `index.html` — エントランス（1カラム ＋ ヒーロー ＋ カードグリッド）

- ヒーロー：全幅、高さ `calc(100vh - var(--header-h))`、背景に生成画像（§9）
  ＋ 暗いグラデーションを重ねて文字のコントラストを確保
- 見出しは `clamp()` で流体サイズ
- 館内案内：4枚のカードグリッド。`repeat(auto-fill, minmax(240px, 1fr))`
- 数字カード3枚（60 / 4 / 56）。`CONTENT.md` §1 の**修正後の表**を使うこと
  （「6冊」のカードは原稿の指示どおり**作らない**）

#### ② `characters.html` — 人物名鑑（マスター＋ディテール）

- 左：9人のリスト（`<ul>` の中に `<button>`）／右：選択中の人物の詳細
- 初期表示はシャーロック・ホームズ
- 人物データは**HTMLに9人分すべて書いておき**、JSは表示/非表示を切り替えるだけにする
  （JS が無効でも全員分の情報が読める。この設計理由をコメントに書くこと）
- 選択中の項目に `aria-current="true"`、詳細領域に `aria-live="polite"`
- 上下矢印キーでリスト内を移動できること
- 768px 以下：リストが上、詳細が下の縦積み。選択したら詳細へスクロールする
- 各人物にポートレート画像（§9）

**マスター＋ディテールの解説をページ内に短く載せること**（3〜4行）。
「左で選ぶと右が変わる型。メールアプリと同じ。狭い画面では2画面に分ける必要がある」

#### ③ `chronology.html` — 年表（1カラム ＋ タイムライン）

- `<ol>` でマークアップする（**順序に意味があるから**。この理由をコメントに書く）
- 年は `<time datetime="1887">` を使う
- 縦の1本線を CSS の疑似要素で描き、各項目に丸い印を置く
- 年のラベルは `position: sticky` でスクロール中に上に留まる
- スクロールで各項目がフェードイン（`IntersectionObserver`）
- 1930年と2023年の間は年月が空くので、**間隔が空いていることが視覚的に分かる**表現にする
- 768px 以下：線を左端に寄せる

#### ④ `works.html` — 作品総覧（2カラム ＋ カードグリッド ＋ 絞り込み）

- 左（`aside`、`position: sticky`）：絞り込み。種別（すべて／長編／短編集）と
  年代（すべて／1880年代…1920年代）。ラジオボタンかチェックボックスを使い、
  `<label>` で必ず紐づける
- 右（`main`）：9冊のカードグリッド。`repeat(auto-fill, minmax(220px, 1fr))`
- 絞り込みは JS で `hidden` 属性を付け外しして実現する（`style.display` は使わない）
- 絞り込み結果の件数を「9件中4件を表示」のように表示し、`aria-live="polite"` を付ける
- 0件になったときのメッセージを用意する
- カードは発表年の昇順で並べる
- 768px 以下：絞り込みが上、一覧が下

#### ⑤ `london.html` — ロンドン地図（スティッキー・スプリット）

- 左（幅 55%）：地図画像（§9）を `position: sticky` で固定。
  画像の上に6つのホットスポット（`<button>`）を `position: absolute` ＋ `%` 指定で配置
- 右（幅 45%）：6か所の解説が縦に並ぶ。スクロールする
- ホットスポットを押すと、対応する解説へスクロールし、両方がハイライトされる
- 右をスクロールすると、画面中央にある解説に対応するホットスポットが光る
  （`IntersectionObserver`）
- **「この地図は正確な縮尺の地図ではなく、位置関係を示す図案です」** の注記を必ず入れる
- 768px 以下：`position: sticky` を解除し、地図の下に解説を縦積み。
  ホットスポットは小さすぎて押せなくなるため、**モバイルでは解説リストを主とする**
  （この判断理由をコメントに書くこと）

### 7.5 「今風」の技法（必ず使い、使った箇所にコメントで理由を書く）

1. `clamp()` による流体タイポグラフィ
2. `backdrop-filter: blur()` によるヘッダーのすりガラス
3. Grid の `auto-fill` + `minmax()` による自動列数調整
4. `:root` カスタムプロパティによる配色の一元管理
5. `scroll-padding-top` によるアンカー移動時のヘッダー被り回避
6. `max-width: 65ch` による可読行長の制御
7. `prefers-reduced-motion` への対応
8. `position: sticky` による追従（サイドバー・年ラベル・地図）

### 7.6 JS の設計原則（違反不可）

- `element.style.xxx = ...` を書かない。**クラス・`data-` 属性・`hidden` 属性の切り替えだけ**
- `scroll` イベントの直接監視をしない。`IntersectionObserver` を使う
  （スクロール中に何百回も関数が呼ばれて重くなるため。この理由をコメントに書く）
- 要素の取得結果を確認してから使う（存在しなくてもエラーで止まらないこと）
- `var` 禁止。`const` / `let` を使う
- **JSが読み込まれなくても、情報はすべて読める状態にしておく**
  （データをJSの中ではなくHTMLに書く。この設計思想をコメントで説明すること）
- コメントは日本語。「何をしているか」ではなく「**なぜそうするか**」を書く
