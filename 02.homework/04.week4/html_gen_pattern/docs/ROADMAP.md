# ROADMAP：どういう順で作り込んでいくか

このディレクトリの現在地と、この先の手順。
**1ステップ＝1回のCodex実行**を単位にしてある。一度に全部作らないのが方針。

- 完成形の設計図 … `SPEC.md`
- 原稿（事実の確定版） … `CONTENT.md`
- 各ステップの実行仕様 … `SPEC_stepN.md`（**STEP1〜7 すべて作成済み**）

**この ROADMAP は概要である。実際に Codex を回すときは `SPEC_stepN.md` を読ませること。**

| ステップ | 実行仕様 | 作るもの |
|---|---|---|
| STEP1 | `SPEC_step1.md` | エントランス（1枚もの） |
| STEP2 | `SPEC_step2.md` | 年表 |
| STEP3 | `SPEC_step3.md` | 人物名鑑 |
| STEP4 | `SPEC_step4.md` | 作品総覧 |
| STEP5 | `SPEC_step5.md` | ロンドン地図 |
| STEP6 | `SPEC_step6.md` | 画像11枚の生成と組み込み |
| STEP7 | `SPEC_step7.md` | 検証・`README.md`・`REPORT.md` |

---

## 方針

> **1ステップごとに、必ず「動くもの」を残す。**

途中で止めても壊れた状態にならないようにする。
また**1ステップにつき新しく学ぶことを1〜2個に絞る**。
まとめて作ると、何が効いているのか分からないまま完成してしまう。

## この先の手順

### STEP3：人物名鑑（`characters.html`）

**採用する型**：マスター＋ディテール（左で選ぶと右が変わる）

**新しく学ぶこと**
- **JavaScript が初めてレイアウトの主役になる。**
  STEP1・2 の JS はハンバーガーとフェードインだけで、無くてもページは成立していた。
  ここからは JS が無いと画面が切り替わらない
- 「データはHTMLに、切り替えだけJSに」という設計
- キーボード操作（上下矢印でリスト内を移動）

**必ず守る設計**
> 9人分のデータは **JSの中ではなくHTMLに全部書く**。JSは表示・非表示を切り替えるだけ。
> こうすると JS が動かなくても9人全員の情報が読める。
> この考え方は、後で英語学習アプリを作るときにそのまま効く。

**判断が要る点**
- 狭い画面ではマスター＋ディテールが成立しない（左右に並ばない）。
  「一覧→タップ→詳細」の2画面にするか、上下に積むか。**上下に積む案を採る予定**
- 人物のポートレート画像は STEP6 まで無い。`aspect-ratio` で場所だけ先に確保しておく

**原稿**：`CONTENT.md` §2（9人分）

---

### STEP4：作品総覧（`works.html`）

**採用する型**：2カラム（Flexbox）＋ カードグリッド ＋ 絞り込み

**新しく学ぶこと**
- **初めての2カラム。** ここで `flex: 1` と `min-width: 0` の意味を体で覚える
- フォーム部品（ラジオボタン・チェックボックス）と `<label>` の紐づけ
- `hidden` 属性による表示制御（`style.display` を使わない理由をここで実感する）
- `aria-live` による「9件中4件を表示」の読み上げ

**判断が要る点**
- 絞り込みの結果が0件になったときの表示を用意する（忘れると無言の空白になる）
- サイドバーを左右どちらに置くか。**操作するものなので左**でもよいが、
  読み物寄りなら右。ここは実際に両方試して決める価値がある

**原稿**：`CONTENT.md` §4（9冊）

---

### STEP5：ロンドン地図（`london.html`）

**採用する型**：スティッキー・スプリット（左に地図を固定、右の解説だけスクロール）

**新しく学ぶこと**
- `position: absolute` と `%` 指定による、画像の上への要素の重ね置き
- `position: sticky` の応用（STEP2 の年ラベルより難しい使い方）
- スクロール位置と表示の連動（`IntersectionObserver` の2度目の実戦）

**判断が要る点**
- **スマホでは成立しない型である。** 地図上の小さな印は指で押せない。
  狭い画面では地図を上に置き、解説リストを主役にする作り替えが要る
- 「この地図は正確な縮尺ではなく位置関係を示す図案です」の注記を必ず入れる

**原稿**：`CONTENT.md` §5（6か所）

---

### STEP6：画像を入れる

**やること**：Codex の画像生成で11枚作り、各ページに組み込む

| 枚数 | 内容 |
|---|---|
| 1 | ヒーロー背景（霧のロンドン、夜、ガス灯） |
| 1 | ロンドン地図（19世紀の古地図風） |
| 9 | 人物ポートレート |

**厳守すること**
- **画像内に文字を描かせない**（生成画像の文字は必ず崩れる）
- **実在の俳優や既存の映像作品に似せない**（ホームズは映像化が多く、肖像権の問題が生じる）
- ポートレート9枚は**画風・照明・構図を統一**する。バラバラだと資料館に見えない
- ヒーローの上には暗いグラデーションを重ね、文字とのコントラスト比 4.5:1 以上を確保

**なぜ最後なのか**
画像を先に入れると、レイアウトが崩れているのか画像が悪いのか切り分けられなくなる。
**構造が固まってから化粧をする**、という順序。
STEP3〜5 の時点で `aspect-ratio` により場所だけ確保しておくこと。

詳細は `SPEC.md` §9。

## 積み残し（負債）

### `GUIDE.md` の §8・§10 が実態と合っていない

中断した実行の名残で、**まだ存在しない資料館5ページと `patterns/` を前提に書かれている**。

対応は2択。
1. STEP7 で、実際に作ったものに合わせて書き直す
2. 該当章を今のうちに削る

**STEP5 まで進めば §8 はほぼ実態に追いつく**ので、1を推す。
`patterns/` を作らないなら §10 だけ削ればよい。

### `patterns/`（型の比較集）は作らないことにした

`SPEC.md` §3・§4 に仕様がある、同一コンテンツを5つの型で作り分ける比較集。
中断して削除済み。**復活させない。**

- **作る理由だったもの**：課題の「調べた証跡」として分かりやすい。型の差分が一目で分かる
- **作らないと決めた理由**：資料館の5ページが既に型を弾き分けており、実質的に役割が重なる。
  型の説明は `NOTES_layout-patterns.md`（タグ構成）と `GUIDE.md`（18パターン）で足りている。
  同じことを3か所で言うより、実物1つと文書2つのほうが管理しやすい

この決定に伴い、`GUIDE.md` §10「実装した5パターンへの索引」は
STEP7 で削除または書き換える（`SPEC_step7.md` §2 に記載）。
`SPEC.md` §3・§4 は**実行されない章**として残る。

- 検索機能

- ビルド設定、Lint設定、パッケージ管理
- デプロイ

## 進め方のルール

1. **1ステップごとに `SPEC_stepN.md` を書いてから Codex を回す。**
   仕様を書かずに指示すると、毎回違うものが出てくる
2. **各ステップの終わりにブラウザで開いて確認する。**
   次のステップに進む前に、気に入らない点は直す
3. **原稿にない事実を書かせない。**
   資料館なので、間違った展示が最悪の失敗。
   Codex が「足りない」と感じても創作させず、報告させて `CONTENT.md` を先に直す
4. **迷ったら止める。** 作り込んでから方針を変えるより、作る前に決めたほうが安い
