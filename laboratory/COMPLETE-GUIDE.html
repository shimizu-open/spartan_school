2.1 OSS とライセンス

用語：OSS（オープンソースソフトウェア）

ソースコードが公開されていて、条件を守れば誰でも使える／改造できる／配布できるソフトウェア。 「無料」という意味ではありません。「条件付きで自由」という意味です。

そして、その「条件」を定めた文書がライセンスです。 ここを軽く見ると、あとで公開できなくなったり、自分のコードまで公開義務が発生したりします。

ライセンスひとことであなたが気をつけること
MITほぼ何でもOK著作権表示を残すだけ。いちばん安全
Apache-2.0MITに特許条項を足したものほぼMITと同じ感覚で使える
BSD-2 / BSD-3MITとほぼ同等安全
MPL-2.0ファイル単位の弱いコピーレフトそのファイルを改造したら公開。自分のコードは巻き込まれない
LGPLライブラリ用のコピーレフトリンク方法によって条件が変わる。要確認
GPL-3.0強いコピーレフト組み込むと自分のコードも同じライセンスで公開する義務
AGPL-3.0GPLのネットワーク版サーバーで動かして公開するだけで、ソース公開義務が発生する
BUSL-1.1OSSではないTerraform等。商用制限あり。一定期間後にOSS化
CC BY文章・画像向け。表示すればOKソフトウェア用ではない。出典表示が必須
CC BY-NC非商用のみThe Odin Project 等。商用利用不可
CC BY-SA継承あり改変したら同じライセンスで公開
OFL-1.1フォント用フォント自体の再配布条件。あなたも使っています
特に注意が必要だったもの（今回の調査で見つかった実例）
  • Terraform は BUSL-1.1 — 現在の新バージョンは厳密には OSI 型 OSS ではない。OSS を重視するなら OpenTofu（MPL-2.0）を選ぶ
  • CheerpX（WebVM の中核）はプロプライエタリ — Community 条件では自己ホストと再配布が許可されない。S3 に置くには商用条件の確認が必要
  • roadmap.sh はコンテンツ再配布禁止 — リンクはOK、転載はNG
  • tldr の本文は CC BY-4.0 — 取り込むなら帰属表示が必須
  • OverTheWire Bandit は OSS ではない — All rights reserved・再配布禁止。リンクのみ
  • pngquant は GPL-3.0 または商用
  • Anki は AGPL-3.0
見落としやすい罠

「GitHub で公開されている」ことと「OSS である」ことは別です。 LICENSE ファイルが無いリポジトリは、法的には「著作権で保護されたまま、何の許可も出ていない」状態です。 公開されていても、勝手に fork して使ってよいわけではありません。
Zenn Book や技術書典系のリポジトリは、サンプルコードだけ OSS で本文は販売物、という構成が多いので特に注意。

2.2 静的サイトと動的サイト

用語：静的サイト（static site）

あらかじめ完成した HTML ファイルを置いておき、そのまま配るサイト。 サーバーは「ファイルを渡す」だけで、何も考えません。

用語：動的サイト（dynamic site）

アクセスがあるたびにサーバーがプログラムを実行し、 データベースを読んで HTML をその場で組み立てて返すサイト。 WordPress や Moodle はこちら。

静的サイト動的サイト
必要なものファイル置き場だけ常時動くサーバー ＋ データベース
費用ほぼ無料サーバー代が毎月かかる
速度非常に速い処理のぶん遅い
壊れにくさ壊れようがないDB障害・更新失敗・攻撃対象になる
保守ほぼ不要セキュリティ更新を怠ると乗っ取られる
できないことログイン、ユーザーごとの表示、書き込み—
なぜこの区別が今回の核心なのか

「学習サイト」と聞くと、多くの人は Moodle のような動的な LMS を思い浮かべます。 しかし LMS が動的である理由は、「受講者が何百人もいて、それぞれの進捗を管理するから」です。

あなたの学習者は一人です。 一人ぶんの進捗なら、サーバーではなくその人のブラウザの中に保存すれば足ります。 だから静的サイトのままで、学習サイトが成立します。これが第9章の結論の土台です。

2.3 ビルドとは何か

用語：ビルド（build）

人間が書きやすい形のファイルを、ブラウザが読みやすい形へ機械的に変換する工程。 「原稿 → 印刷物」の印刷にあたる作業です。

ビルドの中では、だいたい次のような作業が行われます。

作業用語何をするかあなたの現状
まとめるバンドル
(bundle)		バラバラのJSファイルを1つにまとめ、読み込み回数を減らすしていない
小さくするminify
(ミニファイ)		空白・改行・コメントを削り、変数名を短くする64行を手書き
変換するトランスパイル新しい書き方を古いブラウザ向けに書き換えるしていない
指紋を付けるハッシュ付与ファイル名に app.a3f9c1.js のような印を付け、更新時に確実に読み直させるしていない
資産を扱うアセット処理画像を最適化し、CSSを生成し、フォントを配置する手書きで実装
用語：ビルドツール／バンドラ

上の作業をまとめて引き受けてくれる道具。Vite（ヴィート）、esbuild、Rollup、webpack などがあります。 現在の主流は Vite です。あなたが159行かけて自作した build.js は、Vite の設定10〜20行で置き換わります。

2.4 Markdown と frontmatter

用語：Markdown（マークダウン）

記号だけで見出しやリストを表せる、軽い記法。あなたが STUDY.md などで すでに 8,800 行書いているものです。 

# 見出し1
## 見出し2

普通の段落です。**太字** と `コード` が書けます。

- リスト
- リスト

```js
const x = 1;   // コードブロック
```

これが HTML に変換されると <h1> <h2> <p> <strong> <ul> になります。 つまりあなたが記事で手書きしていた HTML タグを、書かなくてよくなります。

用語：frontmatter（フロントマター）

Markdown ファイルの先頭に付ける「この文書についての情報」。 --- で囲んだ部分に書きます。本文には表示されません。 

---
title: 権威DNSサーバーとは
published: 2026-07-01
tags: ["AWS", "DNS"]
draft: false
---

ここから本文
なぜ frontmatter が決定的に重要か

frontmatter があると、プログラムが記事を「読める」ようになります。

いまは記事一覧のカードを index.html に手で書き足していますね。 frontmatter があれば、「全記事の title と published を集めて、 日付順に並べてカードにする」という処理を機械が自動でやります。

記事を1本足す＝Markdownを1枚置く。一覧の更新もリンクも自動。貼り忘れが原理的に起こらない。 これが第4章で出てくる「出版モデル」の正体です。

2.5 データをどこに保存するか

ブラウザの中にデータを保存する方法は主に2つあります。学習の進捗をどこに置くかの話に直結します。

localStorageIndexedDB
扱えるもの文字列だけ構造を持ったデータ、ファイルも可
動作同期（処理中は画面が止まる）非同期（止まらない）
容量の目安約 5〜10 MiBもっと大きい
検索・索引できないできる
難しさとても簡単やや複雑
向いているものテーマ設定、開閉状態など失っても困らないもの学習進捗、復習履歴、イベントログ
絶対に知っておくべきこと：ブラウザの保存は永続保証がない

localStorage も IndexedDB も、ブラウザの都合で消えることがあります。

  • ユーザーが「閲覧データを削除」した
  • プライベートブラウジングだった
  • ストレージが圧迫され、ブラウザが古いデータを捨てた（eviction＝退去）
  • 機種変更した

だから「エクスポート機能」は、あったら良い機能ではなく必須機能です。 navigator.storage.persist() で永続化を依頼できますが、 ブラウザが許可するとは限りません。

現在のコードにある実際の問題

「かけら」の保存処理は QuotaExceededError（容量オーバー）や ストレージ禁止を catch していません。 つまりプライベートブラウジングやストレージ無効設定の環境では、 ユーザーに何も知らせないまま記録が消えます。 保存失敗を通知し、バックアップを促す処理を足すべきです。

2.6 ドメインモデルとは何か

この資料でいちばん重要な概念です。丁寧に説明します。

用語：ドメインモデル（domain model）

「その世界に、どんな“もの”があり、それらがどう関係しているか」を整理したもの。 プログラムを書く前に決める、世界の見取り図です。

「ドメイン」は「対象としている領域」という意味です。 学習サイトのドメインなら、対象は「学ぶこと」の世界。

例で説明します。図書館のドメインモデルを考えてみます。

なぜドメインモデルを先に決めるのか

決めずに作ると、あとで直せなくなるからです。

たとえば図書館で「本」と「貸出」を分けずに、 本のデータの中に「いま誰が借りているか」を直接書いてしまったとします。 最初は動きます。しかし「過去に誰が借りたか」を知りたくなった瞬間に破綻します。 情報がどこにも残っていないからです。

同じことがあなたのゲームでも起きています。Git Dungeon は Gitの状態を firstCommit、mergedFeature といった 真偽値（true/false）の羅列で持っています。動きます。 しかし「コミットがいくつあるか」「どの枝がどこから分かれたか」は、どこにも無いのです。

用語：第一級の概念（first-class concept）

そのシステムが「独立した“もの”として正面から扱っている」もの。 図書館なら「貸出」は第一級。もし貸出を本の属性の一部として持っていたら、それは第一級ではありません。
この資料では「その OSS が何を第一級にしているか」を繰り返し見ます。 それがそのまま「学習サイトに必要な要素」の答えになるからです。

2.7 配信と圧縮

用語：CDN（コンテンツ配信ネットワーク）

世界中にコピーを置いておき、アクセスした人にいちばん近い場所から配る仕組み。 あなたが使っている CloudFront がこれです。

用語：gzip / Brotli と Content-Encoding

ファイルを転送するときだけ自動で圧縮し、ブラウザが自動で解凍する仕組み。 サーバーが「圧縮して送るよ」と Content-Encoding というラベルを付けて送ると、 ブラウザが勝手に元に戻します。プログラムは何もしなくていい。

Brotli は gzip より新しく、よく縮みます。CloudFront は両方に対応していて、 あなたはすでに有効にしています（docs/DEPLOY.md に記載あり）。

これを知らなかったために起きたこと

この仕組みを知らないと、「データを小さくするには、自分で圧縮アルゴリズムを書くしかない」と考えます。 実際 build.js には BPE（Byte Pair Encoding）という圧縮方式が36行、手書きされていました。 そして実測の結果、それは配信サイズをむしろ悪化させていました（12.2節）。

4.3 B. 学習状態モデル ── 詳しく

Frappe LMS、Runestone、CTFd、Tutor LMS といった 「LMS（学習管理システム）」が追加で持っているモデルです。

学校や企業が使う、受講者の学習を管理するためのシステム。 「誰が」「どの講座を」「どこまで進んで」「何点だったか」を記録します。 Moodle、Canvas、Open edX などが代表例。 

Learner                        学習者

│   └── Last visited position     最後にどこを見ていたか

このモデルが持つ「ルール」── ここが設計の勘所

ルール1：完了条件は、種類ごとに違う

これが一番大事です。「完了」の意味は一つではありません。

種類「完了」の判定方法例
読み物閲覧 または 自己申告「読んだ」ボタンを押す
クイズ合格点8問中6問正解
ゲーム・演習クリアイベントゲームが「終わった」と通知する
成果物チェックリストデプロイした・READMEを書いた・振り返りを書いた
ルール2：進捗（Progress）と採点（Score）は別概念

「終わったかどうか」と「どのくらい良くできたか」は違います。 混ぜると、あとで「60点でクリアした人」を表現できなくなります。 Learn Git Branching が「クリア」と「最短手数でのクリア」を分けているのも同じ理由です。

ルール3：ゲームの内部状態と、サイト全体の進捗は別ストアにする

Linux Story Quest の「いまステージ3にいる」という情報と、 サイトの「Linuxコース：演習1つ完了」という情報は別の場所に持つ。 混ぜると、ゲームを作り直したときにサイト全体の進捗まで壊れます。

ルール4：Attempt（挑戦）を何度でも作れるか、制限するかを決める

学習用途では基本的に無制限が正解です。 試験なら制限します。この判断を最初に明文化しておかないと、あとから変えられません。

ルール5：認証を入れた瞬間、責任が発生する

「ログイン機能をつけよう」と思った瞬間に、次のすべてが必要になります。

  • 個人情報の削除機能（求められたら消せること）
  • エクスポート機能（データを持ち出せること）
  • バックアップ（失わないこと）
  • プライバシーポリシー
  • パスワード管理・不正アクセス対策

だから「認証を入れない」ことは、手抜きではなく積極的な設計判断です。 学習者が一人なら、進捗はその人のブラウザに置けばよく、これらの責任は一切発生しません。

6.1 xAPI だけは借りる価値がある

xAPI の中核：actor / verb / object

「誰が・何をした・何に対して」という英語の文の形で学習を記録します。 

{
  "actor":  "local:8f86c44d",                    ← 誰が
  "verb":   "completed",                         ← 何をした
  "object": "unit:web.dns.authoritative-server", ← 何に対して
  "result": { "durationSeconds": 1080 },         ← 結果
  "context":{ "course": "web-foundations",
              "contentVersion": 1 },             ← 文脈
  "timestamp": "2026-08-23T08:18:00.000Z"        ← いつ
}
なぜイベントで記録するのが優れているのか ── 決定的な理由

やりがちなのは、こう書くことです。 

// ❌ 状態を上書きする
progress["web.dns"] = { completed: true };

これでも動きます。しかし「いつ完了したか」「何回挑戦したか」「何日に学習したか」が どこにも残りません。

あとで「ストリーク（連続学習日数）を出したい」と思っても、 元データが無いので計算できません。

イベントとして貯めておけば、ストリークも、総学習時間も、分野別の割合も、 進捗率も、あとから何度でも再計算できます。 集計方法を変えたくなっても、過去のデータを失いません。 これが「イベントソーシング」という考え方です。

使う動詞は9個だけに絞る

opened            開いた
started           始めた
completed         完了した
attempted         挑戦した
passed            合格した
failed            失敗した
reviewed          復習した
bookmarked        しおりを付けた
session-completed 学習セッションが終わった
やらないこと

xAPI互換の LRS（Learning Record Store）を作るのは過剰です。 LRS API、IRI語彙、OAuth、完全な xAPI 検証までは実装しません。 「xAPI-inspired（xAPIに着想を得た）」と明記して、形だけ借ります。

それでも利点は大きい。ゲーム・記事・SRS・かけらが、同じ形式で連携できるようになります。

7.1 完成形

Course（コース）
└── Chapter（章）

        ├── kind: exercise   試す   完了＝ゲームからのイベント／得点
        └── kind: project    作る   完了＝チェックリスト＋URL

    Unit が共通して持つもの:
      id              ← 不変。進捗はこれで参照する（絶対に変えない）
      order           ← 表示順
      prerequisites   ← 前提となる Unit（学習可能性）
      estimatedMinutes← 想定所要時間
      difficulty      ← 難易度
      outcomes        ← 到達目標（何ができるようになるか）
      completion      ← 完了条件の定義
      status          ← draft / published / archived
      contentVersion  ← 内容の版番号

LearnerState（学習者の状態）  ← ここが既存SSGに無い部分。自分で作る
├── UnitProgress    完了状態・最終アクセス・試行回数
├── ReviewCard      復習カード（いつ復習すべきか）
├── Bookmark        しおり（unitId + 見出しID + メモ）
├── ChecklistState  成果物の完了項目
└── LearningEvent   actor / verb / object / result / context / timestamp
この設計の核心：記事も演習も作品も、同じ Unit

分けるのはkind（種類）と完了条件だけです。 順序・前提・所要時間といった性質は全部共通で持たせます。

8演習と正誤判定↑ 目次へ

あなたは学習ゲームを2本自作しています。この章は「教材として正しい判定とは何か」の話です。 ここには、世界の実装が共通して到達している一つの原理があります。

8.1 原理：文字列一致ではなく、状態一致

✗ 悪い判定

input === "cp docs/a.txt atelier/b.txt"

一つの手順しか認めない。
学習者が正しく目的を達成しても、書き方が違えば「不正解」になる。

✓ 望ましい判定

fileExists("/home/student/atelier/b.txt") &&
fileContent("/home/student/atelier/b.txt")
  === originalContent

「どうなったか」だけを見る。
やり方は問わない。

状態で判定すると、次がすべて正解になります。

  • 相対パス（atelier/b.txt）でも絶対パス（/home/student/atelier/b.txt）でも
  • ./atelier/b.txt のような書き方でも
  • 先に cd atelier してからコピーしても
  • 引用符の有無が違っても
  • まったく別の手順で同じ結果に到達しても
なぜこれが「教材として正しい」のか

学習の目的は「特定の文字列を打てるようになること」ではなく、 「目的を達成できるようになること」だからです。
文字列一致で判定すると、学習者は「正解の呪文を覚える」ことを学んでしまいます。 それは目的と違います。

ただし「このコマンドを覚えてほしい」場合は

学習目標が「cp コマンドを知ること」なら、状態だけでは不十分です。 その場合は操作の証拠を追加で要求します。 

goal: {
  state:    { fileExists: "/atelier/b.txt" },   ← 到達すべき状態
  evidence: { commandUsed: "cp" }               ← 使ってほしい操作
}
この章の結論を一文で

正解 ＝ 最終状態の制約 ＋（学習目標に必要な場合のみ）操作の証拠

8.2 判定を三層に分ける

1. 構文受付   parse("cp docs/a.txt atelier/b.txt")  →  AST（構造化データ）
                  ↓
2. 実行       nextState = execute(previousState, ast)
                  ↓
3. 課題判定   grade(nextState, goalConstraints)
用語：AST（抽象構文木）

文字列を、プログラムが扱いやすい構造に変換したもの。 "cp a.txt b.txt" を {command:"cp", args:["a.txt","b.txt"]} のような形にするイメージです。

現在の Linux Story Quest は、すでに良い方向にある

stageSeed が課題ごとの check(ctx) を持ち、 コマンド実行結果の context で判定しています（script.js:67）。
改善点は、ctx.name === "..." を主条件にしすぎず、 仮想ファイルシステムの「実行後の状態」を独立した判定器（grader）に渡すこと。

テスト結果は true/false にしない

{
  testId:   "file-created",
  passed:   true,
  message:  "plan.txt が atelier に作成された",   ← 学習者に見せる説明
  expected: { path: "/home/student/atelier/plan.txt" },
  actual:   { exists: true },
  weight:   1                                     ← 部分点の重み
}

フィードバックを返せるかどうかが、教材としての質を分けます。 「不正解」とだけ言われるのと、「ファイルは作られましたが、中身が違います」と言われるのでは、 学習効果がまったく違います。

8.4 Git の判定 ── Learn Git Branching の設計

Learn Git Branching とは

ブラウザで Git のブランチ操作を学べる、100%クライアントサイドの学習ゲーム。 あなたの Git Dungeon と目的が重なる、世界的に有名な既存教材です。 MIT ライセンス。日本語対応もあります。

各レベルが持っているデータ:

  • startTree ── 開始時のコミットツリー
  • goalTreeString ── 目標のコミットツリー
  • solutionCommand ── 模範解答のコマンド列
  • 説明・ヒント
本質

模範コマンド列を再現したかどうかではなく、 「現在のリポジトリの状態が、目標のグラフと一致するか」で判定している。
8.1節の原理と、まったく同じです。

現在の Git Dungeon の問題

// 真偽値の連鎖で16段階を判定している（script.js:120, 176）
firstCommit, featureCreated, navCommit, mergedFeature,
conflictStarted, conflictResolved, pushed
何が問題か

「コマンドの結果が Git として正しいか」を、自作コード自身が決めています。 つまり教材の正しさを、別の実装で検証できません。

そしてあなたの Git 理解が間違っていた場合、ゲームも一緒に間違います。 学習用の教材でこれは致命的です。誰も間違いに気づけません。

置き換えるモデル

repoState = {
  commits: { C0: { parents: [],     tree: {...} },
             C1: { parents: ["C0"], tree: {...} } },
  refs:    { "refs/heads/main": "C1",
             "refs/heads/feature/nav": "C2" },
  HEAD:    { symbolic: "refs/heads/main" },
  index:   {...},        ← ステージングエリア
  worktree:{...},        ← 作業ツリー
  remotes: {...},
  merge:   { inProgress: false, conflicts: [] }
}

そして課題側は制約で書きます。

goal: {
  branch: "main",
  refs:   { "feature/nav": { mergedInto: "main" } },
  worktree: { clean: true },
  requiredFiles: ["nav.js"]
}

グラフを比較するときの注意

正規化が必要
  • コミットIDそのものを比べない（生成順または構造で再ラベルする）
  • 親子関係を比較する
  • ブランチ・タグが指すノードを比較する
  • HEAD・index・worktree・コンフリクト状態を比較する
  • 無関係な dangling commit（どこからも参照されない孤児コミット）を許すかは、課題ごとに指定する

Learn Git Branching でも、見た目上は同等でも余分な dangling commit があると 不一致になる問題が報告されています（issue #99）。 だから完全一致だけでなく、制約ベースの比較も持つべきです。

両方の調査が一致して「自作継続」を推奨しました

  4. 将来「実シェル」をやりたくなったら Bashkit（MIT・0.x）を実験モードで

8.7 tldr や man から正解を自動生成できるか → できない

tldr（コマンドの実用例集・本文はCC BY-4.0）は機械処理しやすい形式ですが、 代表例集であって、コマンドの完全な仕様でも正解集合でもありません。

→ ヒントや追加の例には使える。正解判定の自動生成には使わない。 使うならビルド時に特定のコミットへ固定し、CC BY-4.0 の帰属表示を行うこと。

9.5 間隔反復（SRS）

用語：SRS（Spaced Repetition System／間隔反復）

「忘れかけたタイミングで復習すると、いちばん効率よく覚えられる」という 認知科学の知見を、アルゴリズムにしたもの。

覚えたてのものは翌日、定着してきたら1週間後、さらに定着したら1ヶ月後……というふうに 復習の間隔を自動で伸ばしていきます。Anki が有名です。

用語：FSRS（Free Spaced Repetition Scheduler）

SRSの最新世代のアルゴリズム。Anki公式も従来のSM-2の代替として採用しており、 同じ時間でより多く保持できる可能性があると説明されています。 標準の目標保持率は90%。保持率を上げるほど復習量が急増します。

名前ライセンス／状況判定
ts-fsrsMIT・v5.4.1（2026-06）採用。TypeScript実装、Node 20以上
Anki本体AGPL-3.0-or-later・26.05系（2026-06）サイトにSRSを再実装しないなら、まずこれを別アプリとして使う
SM-2—実装は単純だが、新規に選ぶ理由は少ない
RecallMIT・v1.2.0（2026）非常に新しい小規模プロジェクト。実験用途
最重要の注意：FSRSの対象は「レッスン」ではなく「思い出せる単位のカード」

✗ 悪い例

「DNSの記事を復習する」

→ 大きすぎて「思い出せたか」を判定できない

✓ 良い例

「再帰DNSと権威DNSの違いを説明する」

→ 思い出せたか自分で判定できる

評価は Again（もう一度）／Hard（難しい）／Good（普通）／Easy（簡単） の4段階。
初期は標準パラメータのまま。数百件のレビュー履歴が貯まるまで、個人最適化はしない。

Starlight を採る理由:

  1. next-course-starter は Next.js / React。あなたは素のJavaScriptで書いてきたので、Reactは新規学習になる。第1ラウンドの調査でも「Next.jsは既存HTMLのJSX化コストが最大、このサイトには過剰」と判定済み
  2. next-course-starter は「GitHub Releasesなし、最終コミット日は未確認」（調査自身の記述）。Starlightは v0.41.5（2026-07-28） で公式保守
  3. 既製品の調査自身が、退路としてStarlightを挙げている ——「スターター固有の古さやNext.js更新問題が大きければ、コンテンツ構造を保ったまま公式Starlightへ移る」
  4. next-course-starter の利点は Course / Section / Lesson を第一級概念に持つことだが、それは9.3節のfrontmatterでStarlightに足せる
  5. 手書きのヴィクトリア朝CSS 303行を保つには、Astro系が有利

12.1 手書き minifier は「不完全なJavaScript字句解析器」だった

build.js の64行は、JavaScriptを1文字ずつ走査して空白とコメントを除く処理でした。 しかし現実のJavaScriptは、それだけでは解析できません。

破壊パターン① 正規表現リテラルと除算の区別ができない

const result = value / /x/.test(text);

最初の / は割り算、次の / は正規表現の開始です。空白を消すと:

const result=value//x/.test(text);   ← // 以降が全部コメント扱いになる

/ が「除算・正規表現・コメント」のどれかは、 前後1文字では判断できず、構文上の位置を理解しなければなりません。

破壊パターン② テンプレートリテラルの中身を書き換えてしまう

現在の処理はすべてのテンプレートリテラル内部に対して replace(/\s+/g," ") を実行します。 HTML以外でも改行や連続スペースをデータとして使う可能性があるため、 通常の文字列値が変わってしまいます。 

`outer ${`inner ${value}`}`

さらに、${...} の中をJavaScriptとして再帰的に解析していないため、 内側のバッククォートを外側の終了と誤認します。

破壊パターン③ ASI（自動セミコロン挿入）を無視している

用語：ASI（Automatic Semicolon Insertion）

JavaScriptが改行の位置に自動でセミコロンを補う仕様。 だから改行を消すと意味が変わることがあります。 

function f() {
  return
  { ok: true };
}

元は undefined を返します（return の直後にASIが働く）。 しかし改行を消すとオブジェクトを返すようになり、意味が変わります。 

a
++b

ASIにより本来2文ですが、このminifierでは a++b となり構文エラーになります。

結論

この64行は「単純なminifier」ではなく、「不完全なJavaScript字句解析器」になっています。
いま動いていても、書き方を変えた瞬間に静かに壊れたコードを吐きます。 学習用に一度作る価値はありましたが、本番のビルドに残してはいけません。

12.3 実在したバグ ── DST（サマータイム）

用語：DST（Daylight Saving Time／夏時間・サマータイム）

一部の国で、夏の間だけ時計を1時間進める制度。 切り替わる日は「23時間の日」や「25時間の日」が発生します。

lib/date.js には「正午に固定する」という優れた工夫が入っていました。 これは日付文字列のずれを避けるうえで有効です。しかし daysBetween は依然として安全ではありませんでした。 

export function daysBetween(first, last = dateKey()) {
  return Math.floor((fromDateKey(last) - fromDateKey(first)) / DAY);
}

DST開始日をまたぐと、正午どうしの間隔が23時間になり、 Math.floor(23 / 24) === 0 になります。

実際に実行して再現した結果:

TZ=America/New_York （DSTあり）
  2026-03-07 → 2026-03-08 の日数差: 0    ← 期待値 1
  60日開放: 2026-02-01 → 2026-04-02 : 59  ← 期待値 60（開放が1日遅れる）

TZ=Asia/Tokyo （DSTなし）
  2026-03-07 → 2026-03-08 の日数差: 1    ← 正常
  60日開放: 2026-02-01 → 2026-04-02 : 60  ← 正常
重要な但し書き

バグは実在します。ただし日本（JST）にはDSTがないので、国内の利用者には現れません。
「今壊れている」のではなく「DSTのある地域の端末で使われたら壊れる」種類のバグです。 だから優先度は低い。

直し方

differenceInCalendarDays だけ date-fns に置き換えます。 この関数は「24時間の経過」ではなく「カレンダー上の日付差」を計算するので、 定義上DSTの影響を受けません。

14.8 CSSの土台 ── クラスレスCSSは「導入しない」

用語：クラスレスCSS

CSSを1枚読み込むだけで、class属性を書かなくても素のHTMLが整って見えるライブラリ。 Pico.css、Water.css、Simple.css など。

学習サイトには理論上 Pico.css か Simple.css が合いますが、今回は導入しないのが妥当です。

assets/style.css はすでに色・書体・カード・記事・表・コード・ナビを一貫して定義しています。 クラスレスCSSを足すと、303行が減るのではなく「外部CSSを打ち消す上書き」が増えます。
→ クラスレスCSSの適所は、今後作る一時的な授業メモや検証HTMLです。

CSSの最終結論:

  • Pico等のクラスレスCSSは重ねない
  • modern-normalize は必要なら土台だけ借りる
  • Open Props は余白・easeの考え方だけ借りる
  • CUBE CSS と @layer で既存CSSを整理する
  • 機械チェックを入れるなら stylelint を第一候補に
  • vanilla-extract / Panda / PostCSS単体導入はしない
