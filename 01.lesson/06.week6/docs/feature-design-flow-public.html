第1部　考え方の流れ

1この資料が答える4つの問い共通

教材を写して動かせるようになったあと、多くの人がここで止まります。

問い答えがある章
機能を足すとき、何から考えればいい？2章〜4章
ということは、◯◯を作るなら何と何が必ず要る？5章
なぜその順番で作るの？8章
なぜその部品が必要なの？ どこに何を書くの？9章〜11章

身につけたいのは「機能を足すときの考え方」で、これはフレームワークや言語が変わっても同じです。Laravel は、その考え方を動くコードで確かめるための題材として使います。例は ToDo アプリ（タスクの一覧・作成・編集・削除ができている状態）です。

見出しの印意味
共通どのフレームワークでも同じ考え方。ここが本題です
Laravelその考え方を Laravel でどう書くか。他のフレームワークなら名前が変わるだけです

2よくある流れと、実際の流れ共通

機能を足すとき、多くの人はこういう流れを思い浮かべます。骨格としては正しいです。

どんな機能が必要か → 何を考えるか → 何が必要か → どの順で作るか → どこに何を書くか → 動くまで

ここまではフレームワークに関係のない話です。実際に手を動かしている人の頭の中は、ここに4つ足されています。

足されるもの中身
① 「何を考えるか」の正体は
ルールを質問で引き出すこと		「タスクに手順を付けたい」だけでは作れません。何件まで？ 消したらどうなる？ 空でもいい？ と自分に質問して、答えを決める。コードの大半は、この答えを書き写したものです。
② 名詞と動詞に分ける「何が必要か」を機械的に出す方法。名詞 → テーブル、動詞 → URLとコントローラのメソッドになります。
③ 考える向きと作る向きは逆考えるのは画面（外）からデータ（内）へ。作るのはデータ（内）から画面（外）へ。
④ 1本ずつ通して、その都度確かめる全部書いてから動かすのではなく、「表示だけ」「追加だけ」と細く1本通して確認してから次へ。エラーの原因が直前に書いた数行に絞られます。
もう1つ正直な話：この流れは一直線には進みません。作っている途中で「あ、消したときのことを決めてなかった」と気づいて前の段に戻る、を何度もやります。戻るのは失敗ではなく、普通の進み方です。

3全体図：考える向きと作る向きは逆共通

左で決めたことは、同じ高さの右で確かめます。③で「1タスクに1つだけ」と決めたなら、⑦で「2つ目を作ろうとして弾かれる」ことを確かめる、という対応です。

なぜ画面から考えるのか
使う人に見えるのは画面だけだからです。テーブルから考え始めると「使われない列」や「足りない列」が出ます。画面での操作を先に書き出すと、必要なデータが逆算できます。
なぜデータから作るのか
画面はデータが無いと何も表示できず、確認できないからです。さらに、テーブルの形は後から変えるのが一番大変（既存データがある）なので、最初に固めます。画面は後からいくらでも直せます。

49ステップを1つずつ共通

①

何がしたい？ ― 1文で書く

「誰が・何に・何をしたい」。技術の言葉（テーブル、外部キー）はまだ使いません。
例：「大きなタスクを細かい手順に分けて、1つずつ片付けたい」

②

画面でどう使う？ ― 動詞を全部書き出す

どの画面で、何を押して、何が起きて、そのあとどの画面にいるか。「やらないこと」もここで決めます（例：手順の並べ替えは作らない）。作る量はここで決まります。

第2部　何が要るかを決める

5「◯◯を作るなら何が必ず要る？」は、3つの問いで決まる共通

「機能ごとに必要な部品を覚える」必要はありません。足したい機能について、次の3つを確かめれば部品が出ます。3つは別々の問いなので、全部に答えます（「はい」が2つ以上になることも普通です）。

機能の例もの性質操作必ず要る部品
タスクに「手順」を付けて、1つずつ完了にするはい―はいテーブル・モデル・関係の宣言 ＋ ルート・コントローラ・フォーム
タスクに締め切り日を付ける―はい―列の追加 ＋ 既存フォームに入力欄 ＋ 入力チェック
タスクをプロジェクトにまとめるはいはい―（※）テーブル・モデル・関係の宣言 ＋ 既存テーブルに列 ＋ 既存フォームに選択欄
ボタン1つで「完了／未完了」を切り替える――はいルート ＋ コントローラのメソッド ＋ ボタン
未完了だけ表示する、締め切り順に並べる―――既存の一覧処理と画面を直すだけ

※ プロジェクト自体を画面から作らせるなら「操作」も「はい」になり、プロジェクト用のルート・コントローラ・画面が増えます。

部品は2つのグループに分かれます。
・データのつながり：テーブル（または列）、モデル、関係の宣言。これだけで対話環境からは使えます。
・人が触る入口：ルート、コントローラ、画面。「その操作に専用のボタンやURLが要るか」で、新しく作るか既存に足すかが決まります。

6「もの」が増えるとき：なぜテーブルを分けるのか共通

「タスクに手順を付けたい」と思ったとき、いちばん素朴な発想は今のテーブルに列を足すことです。やってみると、すぐ行き詰まります。

✕ 素朴案：tasks に step 列を足す
idtitlestep1step2step3
1勉強会の準備スライドを作る会場を予約する（空）
2買い物牛乳を買う（空）（空）
4つ目の手順が来たら列を足すためにテーブルを変更。手順が無いタスクは空欄だらけ。「手順ごとの完了チェック」を持たせようとすると列がさらに倍になります。何件になるか分からないものは、列では持てません。
○ 手順は別のテーブルにして、1件＝1行にする
行は何行でも増やせます。ただし別テーブルにすると「この手順は、どのタスクのもの？」が分からなくなる。そこで手順の行に「タスクの番号を書く欄」を足します。これが外部キー（task_id）です。

逆に、1つのタスクに必ず1つしか無い情報（締め切り日、優先度）は、列を足すだけで済みます。「もの」か「性質」かの見分け方はここです。

7つなぎ方は3種類。違いは「番号欄をどこに置くか」だけ共通

オレンジ色の列が外部キー（番号欄）、矢印が「この番号の行を指している」です。

1対多：番号欄は「多」の側に置く

task_id に同じ「1」が何回出てきてもよい → だから1つのタスクに手順が何件でも付く。逆に tasks 側に step_id を置くと1つしか書けません。だから番号欄は「多」の側。

1対1：1対多に「同じ番号は1回だけ」を足しただけ

テーブルの形は1対多と同じ。番号欄に一意制約（unique）を付けるだけ。「1件まで」を守っているのはアプリのコードではなくデータベースです。

1対1は、たいてい列で足ります。 締め切り日のように値が1つなら、別テーブルにせず列を足すほうが単純です。別テーブルにするのは、①その情報が複数の列のかたまりで、②ほとんどの行には無く、③本体とは別のタイミングで設定・解除する、といった場合です（図の「繰り返し設定」がその例）。

多対多：どちらに置いても足りない → 「線だけのテーブル」を真ん中に作る

タスクに担当者は何人でも、担当者もタスクをいくつでも。どちらも「多」なので、どちらのテーブルにも番号欄を置けない → 番号欄2つだけのテーブルを別に作ります。担当に入れる＝行が増える、外す＝行が消える。

どれになるかは、質問2つで決まる

Q1. Aひとつに、Bはいくつ？Q2. Bひとつは、Aいくつに付く？答え番号欄の置き場所
たくさん1つだけ1対多B のテーブルに「A の番号」
1つだけ1つだけ1対1A に列を足す。または B のテーブルに「A の番号」＋一意制約
たくさんたくさん多対多中間テーブルに「A の番号」と「B の番号」

8なぜ「奥から手前へ」作るのか共通

教材の手順はたいてい マイグレーション → モデル → migrate → コントローラ → ルート → ビュー。これはリクエストが流れる向きのちょうど逆です。

倉庫が無いのに通訳は雇えない。通訳がいないのに担当者は指示できない。担当者がいないのに受付は案内できない。窓口（フォーム）は送り先のURLが決まってから作る。

本当に順番が固定のところ
  • 親のテーブル → 子のテーブルの順（tasks → steps）。外部キーは「指す先」が先に存在しないと作れない（中間テーブルは、つなぐ両方のテーブルが先に必要）
  • migrate はデータを触る前に。ファイルを書いただけではテーブルは出来ていない
実はどの順でも動くところ
  • Model／Controller／Route／View を書く順番。画面を開く瞬間に全部そろっていればOK
  • 奥から作るのは「途中で確認しやすい」から。テーブル＋モデルだけで tinker で試せる

10関係の宣言：番号欄を持つ側が belongsToLaravel

テーブルを作っただけでは、Laravel は「どの列でつながっているか」を知りません。モデルにメソッドを書いて教えます。どれを書くかは、番号欄の場所で自動的に決まります。

自分のテーブルに ○○_id が…書くもの読み方
あるbelongsTo「私は相手の番号を持っている＝相手に属している」
ない（相手は複数）hasMany「相手のテーブルから、私の番号が書かれた行を全部探して」
ない（相手は1件）hasOne「相手のテーブルから、私の番号が書かれた行を1件探して」
どちらにもない（中間テーブルにある）両方 belongsToMany「中間テーブルを経由して探して」
// app/Models/Task.php … task_id を持っていない側
public function steps()
{
    return $this->hasMany(Step::class);      // 相手（steps）の task_id を見に行く
}

// app/Models/Step.php … task_id を持っている側
public function task()
{
    return $this->belongsTo(Task::class);    // 自分（steps）の task_id を使う
}

宣言しておくと、SQL を書かずにこう書けます。

$task->steps                       // このタスクの手順ぜんぶ
$task->steps()->create([...])      // task_id を自動で入れて1行追加
$step->task                        // この手順の親タスク
向きを逆に書くと、エラーにならずに空が返ることがあります。 Task に belongsTo(Step::class) と書くと、Laravel は tasks テーブルの step_id を探します。そんな列は無いので、結果はいつも null です。「関係が取れない」ときは、まず向きを疑います。

第4部　例で通す（ToDo アプリ）

13通し例2：プロジェクトでまとめる（同じ質問、違う答え）Laravel

「タスクをプロジェクトごとにまとめたい」。これも1対多ですが、今度は今あるタスクが「多」の側です。番号欄は「多」の側に置くので、既存の tasks テーブルに列が増えます。

通し例1では新しいテーブル（steps）に番号欄がありました。今回は既存のテーブル（tasks）に番号欄を足します。どちらに足すかは「どちらが多か」で決まります。

質問通し例1（手順）の答え今回（プロジェクト）の答え → コード
どちらが「多」？新しく作る手順既存のタスク → Schema::table('tasks', …) で project_id を足す。Task が belongsTo、Project が hasMany
親なしでもいい？ダメ（手順は必ずタスクに付く）いい（どこにも入れないタスクがある） → ->nullable()、'project_id' => 'nullable|exists:projects,id'
親を消したら？一緒に消えるタスクは残して、所属だけ外す → ->nullOnDelete()
いつ操作する？単独で（専用のボタン）タスクの作成・編集のついでに選ぶ → 専用ルートなし。既存フォームに選択欄、$fillable に project_id
誰が作るデータ？使う人決めること。最初は初期データで数個入れておき、あとで作成画面を足してもよい
一覧にも出す？件数だけプロジェクト名を出す → Task::with('project')
// tasks に列を足すマイグレーション（projects テーブルを先に作っておく）
Schema::table('tasks', function (Blueprint $table) {
    $table->foreignId('project_id')->nullable()->constrained()->nullOnDelete();
});
「親を消したら？」の答えが変わると、コードは1語だけ変わります（cascadeOnDelete → nullOnDelete）。しかし使う人にとっては「タスクが全部消える」か「残る」かの大きな違いです。コードの量と、決めることの重さは比例しません。

一覧で関連を表示するときの落とし穴（N+1）

まとめ読みなし（11回） 
タスク10件ください         ← 1回
タスク1のプロジェクトは？   ← +1
タスク2のプロジェクトは？   ← +1
 …
タスク10のプロジェクトは？  ← +1
ループの中で $task->project に触るたび、その場で SQL が走ります。100件なら101回。
with('project') あり（2回） 
タスク10件ください         ← 1回
そのタスクのプロジェクトを
まとめてください            ← 1回
先にまとめて取り、各タスクに配ります。何件でも2回。

これは Laravel に限らず、モデル経由でデータを取る仕組み（ORM）全般で起きます。「ループの中で関連に触るなら、先にまとめて読む」と覚えておけば足ります。

14通し例3：テーブルが増えない機能（締め切り・絞り込み）Laravel

同じ流れで考えると、「今回は新しいテーブルは要らない」と分かる機能があります。作らないと判断するのも設計です。

締め切り日を付ける（「性質」が増える）

ステップ考えたこと
② 画面作成・編集フォームで日付を選ぶ。一覧と詳細に出す
③ ルール1つのタスクに締め切りは1つ。無くてもいい。過去の日付は？（決める：編集時に困るので許す）
④ データ値が1つだけ → 列で足りる。$table->date('due_date')->nullable()
⑤ 作る列追加のマイグレーション → $fillable と casts（日付として扱う） → バリデーションに 'due_date' => 'nullable|date' → フォームに入力欄 → 表示
新しく作らないものテーブル、モデル、ルート、コントローラ。既存の保存処理にそのまま乗る

未完了だけ表示する・締め切り順に並べる（「見方」が増える）

ステップ考えたこと
② 画面一覧で「未完了だけ」を選ぶと絞り込まれる。締め切りが近い順に並ぶ
③ ルール何も選ばなければ全部。締め切りが無いタスクはどこに並ぶ？（決める：最後）。ページを送っても絞り込みは続く
④ データ追加なし。「見る」の条件が増えるだけなのでルートも追加なし（GET /tasks?status=open）
⑤ 作る一覧の処理に条件と並び順を足す → 一覧に絞り込みリンク
$tasks = Task::with('project')
    ->when($request->query('status') === 'open', fn ($q) => $q->where('is_done', false))
    ->orderByRaw('due_date is null')   // 締め切りなしを最後に
    ->orderBy('due_date')
    ->paginate(10)
    ->withQueryString();               // ページ送りでも ?status=open を引き継ぐ
「締め切りなしはどこに並ぶ？」は、書いてみるまで気づきにくいルールです。 何も決めずに orderBy('due_date') と書くと、MySQL では締め切りなしが先頭に来ます。動かして「あれ？」と思ったら、③に戻ってルールを足す。この往復が普通の進み方です。

16教材を「考える練習」に変える方法共通

教材は④（データの形）までが済んだ状態で渡されるので、上から写すだけでは①〜④の練習になりません。同じ教材を練習に変える方法は次の3つです。

  1. 写し終えたコードは、逆向きに読む。 1行ずつ見て「これはどのルールを書いたもの？」を言う。12章のような「ルール → コード」の対応表を自分で作ってみる。
