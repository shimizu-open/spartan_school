第1部　考え方の流れ

1あなたの流れと、実際の流れ

あなたが書いた流れは、骨格として正しいです。

どんな機能が必要か → 何を考えるか → 何が必要か → どの順で作るか → どこに何を書くか → 動くまで

実際に手を動かしている人の頭の中は、ここに4つ足されています。

足されるもの中身
① 「何を考えるか」の正体は
ルールを質問で引き出すこと		「コメントを付けたい」だけでは作れません。何件まで？ 消したらどうなる？ 空でもいい？ と自分に質問して、答えを決める。コードの大半は、この答えを書き写したものです。
② 名詞と動詞に分ける「何が必要か」を機械的に出す方法。名詞 → テーブル、動詞 → URLとコントローラのメソッドになります。
③ 考える向きと作る向きは逆考えるのは画面（外）からデータ（内）へ。作るのはデータ（内）から画面（外）へ。
④ 1本ずつ通して、その都度確かめる全部書いてから動かすのではなく、「表示だけ」「追加だけ」と細く1本通して確認してから次へ。エラーの原因が直前に書いた数行に絞られます。
もう1つ正直な話：この流れは一直線には進みません。作っている途中で「あ、消したときのことを決めてなかった」と気づいて前の段に戻る、を何度もやります。戻るのは失敗ではなく、普通の進み方です。

2全体図：考える向きと作る向きは逆

左で決めたことは、同じ高さの右で確かめます。③で「1メモに1つだけ」と決めたなら、⑦で「2つ目を作ろうとして弾かれる」ことを確かめる、という対応です。

なぜ画面から考えるのか
使う人に見えるのは画面だけだからです。テーブルから考え始めると「使われない列」や「足りない列」が出ます。画面での操作を先に書き出すと、必要なデータが逆算できます。
なぜデータから作るのか
画面はデータが無いと何も表示できず、確認できないからです。さらに、テーブルの形は後から変えるのが一番大変（既存データがある）なので、最初に固めます。画面は後からいくらでも直せます。

39ステップを1つずつ

①

何がしたい？ ― 1文で書く

「誰が・何に・何をしたい」。技術の言葉（テーブル、外部キー）はまだ使いません。
例：「メモを読み返したときに、あとから思いついたことを書き足したい」

②

画面でどう使う？ ― 動詞を全部書き出す

どの画面で、何を押して、何が起きて、そのあとどの画面にいるか。「やらないこと」もここで決めます（例：コメントの編集は作らない）。作る量はここで決まります。

③

第2部　道具：リレーションと作る順番

4リレーションとは：なぜテーブルを分けるの？

「メモにコメントを付けたい」と思ったとき、いちばん素朴な発想は memos テーブルに列を足すことです。やってみると、すぐ行き詰まります。

✕ 素朴案：memos に comment 列を足す
idtitlecomment1comment2comment3
1買い物リスト牛乳も買う卵は特売日に（空）
2企画のたね来週までに案出し（空）（空）
4件目のコメントが来たら？ → 列を足すためにテーブルを作り直し。コメントが0件のメモは空欄だらけ。「何件書かれるか分からないもの」は列では持てません。
○ 正解：コメントは別のテーブルにして、1件＝1行にする
行は何行でも増やせます。ただし別テーブルにすると 「このコメントは、どのメモのもの？」が分からなくなる。
そこで、コメントの行に「メモの番号を書く欄」を1つ足します。これが memo_id ＝ 外部キーです。

リレーション ＝ 「別テーブルに分けたものを、番号でつなぎ直す仕組み」。これだけです。

53種類の違いは「番号欄をどこに置くか」だけ

オレンジ色の列が外部キー（番号欄）、矢印が「この番号の行を指している」です。

A-1｜1対多（メモ ─ コメント）：番号欄は「多」の側に置く

memo_id に同じ「1」が何回出てきてもOK → だから1つのメモにコメントが何件でも付く。
逆に memos 側に comment_id を置くと、1つしか書けないので「多」になれません。だから番号欄は「多」の側。

A-2｜1対1（メモ ─ リマインダー）：1対多に「同じ番号は1回だけ（unique）」を足しただけ

テーブルの形は1対多とまったく同じ。違いは ->unique() の一言だけ。「1件まで」を守っているのは PHP ではなくデータベースです。

A-3｜多対多（メモ ─ タグ）：どちらに置いても足りない → 「線だけのテーブル」を真ん中に作る

memos に tag_id を置くとタグは1つしか付かない。tags に memo_id を置くとそのタグは1つのメモにしか付かない。どちらも「多」なので、どちらにも置けない → 番号欄2つだけのテーブルを別に作る。チェックを付ける＝行が増える、外す＝行が消える。

どれを選ぶかは、質問2つで決まる

Q1. メモ1つに、相手はいくつ？Q2. 相手1つは、メモいくつに付く？答え番号欄の置き場所
たくさん1つだけ1対多相手のテーブルに memo_id
1つだけ1つだけ1対1相手のテーブルに memo_id ＋ unique()
たくさんたくさん多対多中間テーブルに memo_id と tag_id

6hasMany / belongsTo は「番号欄がどっちにあるか」の申告

テーブルを作っただけでは、Laravel は「どの列でつながっているか」を知りません。モデルにメソッドを書いて教えます。書き方は番号欄の場所で自動的に決まります。

自分のテーブルに ○○_id が…書くもの読み方
ある（Comment, Reminder）belongsTo「私は相手の番号を持っている＝相手に属している」
ない（Memo）相手は複数hasMany「相手のテーブルから、私の番号が書かれた行を全部探して」
ない（Memo）相手は1件hasOne「相手のテーブルから、私の番号が書かれた行を1件探して」
どちらにもない（Memo と Tag）両方 belongsToMany「中間テーブルを経由して探して」

これを書くと、SQLなしでこう書けるようになります。メソッドを書く理由はこの「便利さ」のためです。

$memo->comments                    // このメモのコメント全部（SELECT * FROM comments WHERE memo_id = 1）
$memo->comments()->create([...])   // memo_id を自動で入れて INSERT
$comment->memo                     // このコメントの親メモ
$memo->tags()->sync([1, 3])        // 中間テーブルの行を「ちょうど 1 と 3」にそろえる
だから Comment の $fillable に memo_id が無くても大丈夫。 $memo->comments()->create() が「このメモの」番号を勝手に入れてくれるからです。フォームから memo_id を受け取らないので、他人のメモ番号を送りつけられる心配もありません。

7⑤の補足：なぜ「奥から手前へ」作るのか

レッスンの手順は毎回 マイグレーション → モデル → migrate → コントローラ → ルート → ビュー。これはリクエストが流れる向きのちょうど逆です。

倉庫が無いのに通訳は雇えない。通訳がいないのに担当者は指示できない。担当者がいないのに受付は案内できない。窓口（フォーム）は送り先のURLが決まってから作る。

本当に順番が固定のところ
  • memos テーブル → comments テーブルの順。外部キーは「指す先」が先に存在しないと作れない（中間テーブルは memos も tags も先に必要）
  • migrate はデータを触る前に。ファイルを書いただけではテーブルは出来ていない
実はどの順でも動くところ
  • Model／Controller／Route／View を書く順番。画面を開く瞬間に全部そろっていればOK
  • 奥から作るのは「途中で確認しやすい」から。テーブル＋モデルだけで tinker で試せる

10A-2・A-3：ルールが違うとコードがどう変わるか

A-1 と同じ質問をして、答えが違ったところだけコードが変わります。

A-2 リマインダー ― 「いくつ？」の答えが「1つだけ」

決めたルールコードになった姿
1つのメモにリマインダーは1つだけforeignId('memo_id')->unique()、hasOne、メソッド名が単数形 reminder()
すでにあるときに設定したら上書きupdateOrCreate([], $validated)。「追加」ではなく「設定」なので POST ではなく PUT
1つしか無いので番号で選ぶ必要がないURLが /memos/{memo}/reminder（リマインダーのIDが出てこない）
解除できるDELETE /memos/{memo}/reminder
日時として表示・比較したいモデルの casts() で 'datetime'
メモを消したら一緒に消えるcascadeOnDelete()（A-1と同じ）
レッスンが決めていないルールもあります。「過去の日時を設定していい？」。レッスンのバリデーションは required|date だけなので、過去でも通ります。ダメにしたいなら after:now を足す。こういう「決めていなかったこと」に気づけるのが、③の質問を自分でやる意味です。

A-3 タグ ― 「いくつ？」が両方「たくさん」、「誰が作る？」「いつ操作する？」も違う

決めたルールコードになった姿
メモにタグはたくさん、タグもメモにたくさん中間テーブル memo_tag、両方 belongsToMany
同じメモに同じタグは2回付かないprimary(['memo_id', 'tag_id'])
同じ名前のタグは作らないstring('name', 20)->unique()
タグは使う人が作らない（最初から用意）TagSeeder。タグを作る画面・TagController は作らない
タグはメモの作成・編集のついでに付ける専用ルートなし。_form にチェックボックス、MemoController の store / update に sync()
タグは0個でもいい'tags' => 'array'（required なし）、input('tags', [])
存在しないタグ番号は受け付けない'tags.*' => 'exists:tags,id'
メモを消したら線も消える。タグを消してもメモは残る中間テーブルの外部キー2本に cascadeOnDelete()
一覧にもタグを出すMemo::with('tags')
もしルールを「タグは使う人が自由に作れる」に変えたら？ → Seeder は要らなくなり、タグを作るフォーム・ルート・TagController が要ります。
「何を作るか」は、技術ではなくルールの答えで決まる、という例です。

なぜタグだけ Controller と Route を作らないの？
コメントとリマインダーは「メモとは別のタイミングで、単独で追加・削除する」ので、専用のURL（入口）が要ります。
タグは「メモを保存するときに、ついでにチェックを送る」だけ。入口はメモの保存と同じなので、既存の MemoController に足せば済みます。タグそのもの（「重要」など）を画面から作る機能は無いので、Seeder で先に入れています。
→ 判断基準は「その操作に専用のボタン／URLが要るか」です。

ステップ考えたこと

② 画面詳細画面のボタンを押すたびに、ピン留め ⇄ 解除。押したあとは同じ画面

ステップ考えたこと

機能の種類テーブルモデルルートコントローラビュー

15この課題での練習のしかた

レッスンは④までが済んだ状態で渡されるので、上から貼るだけでは①〜④の練習になりません。同じ教材で練習にする方法は次の3つです。

  1. A-1（済んでいる分）は逆向きに読む。 コードを1行ずつ見て「これはどのルールを書いたもの？」を言う。9章の表が答え合わせです。
  2. A-2・A-3 は、コードを見る前に設計シートを埋める。 見出しの1文（「1つのメモにリマインダーは1つだけ」）だけ読んで、テーブル・URL・コントローラのメソッドを自分で予想する。そのあとレッスンのコードと比べ、違ったところの理由を考える。10章の表が答え合わせです。
  3. 課題B は、シートを埋めてから書く。 ここは答えが無いので、本番と同じ条件です。まず13章の早見表で「新しい名詞はあるか、新しい動詞はあるか」から。
予想とレッスンが違っていても、動けばどちらも正解のことが多いです（例：コメント削除のURLを /memos/{memo}/comments/{comment} にしても動きます）。大事なのは「なぜそうしたか」を自分のルールで説明できることです。
