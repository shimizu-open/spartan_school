外から来たものは、信用しない

MASS ASSIGNMENT ・ SQL INJECTION
「画面に無い」は守りではない。受け取る枠を、先に自分で決める。
1

前提：フォームは「お願い」でしかない

知らないと、ここで油断する
1送信内容は、利用者の手元で作られる
ブラウザが組み立てた文字を、サーバーは受け取るだけ。中身を選ぶ権利はない。
2項目も値も、いくらでも書き換えられる
開発者ツールで欄を足す、コマンドで直接送る。特別な技術はいらない。
!だから、こう考える
「欄を置いていない項目は届かない」は成り立たない。何が届いてもよい作りにする。
2

列の守り：どの列に書くかを、外に決めさせない

マスアサインメント（一括代入）
届いたものを、全部書き写すDANGER
Model::create($request->all());
// 届いた「項目名」が、そのまま「列名」になる
// 画面に欄が無くても、DBに列があれば書き込まれる
権限のような「利用者に触らせない列」まで上書きされる
▶
枠を決める
枠の中だけ、書き写すSAFE
protected $fillable = [/* 許可する列だけ */];
Model::create($request->validated());
// 枠に無い項目は、届いても黙って捨てられる
ホワイトリスト：書いた列「だけ」を受け入れる
3

同じ考え方が、もう1か所に出てくる

列の枠と、命令の枠

列の枠ホワイトリスト $fillable

守るもの：どの列に書くかを、外から決めさせない。
ブラックリスト $guarded 書き忘れた列は許可される。後から列を足すたびに穴になりうる。
ホワイトリスト $fillable 書き忘れた列は拒否される。失敗しても安全な側に倒れる。

命令の枠プリペアドステートメント

守るもの：SQL の命令の形を、外から変えさせない。
入力を文章につなげる 命令を読む前に入力が混ざる。記号で値の枠を閉じられ、続きが命令として読まれる。
? で穴を空け、値は別に渡す 命令を読んで形を確定した後に値が届く。何が来ても「ただの文字」。
4

プリペアドステートメントの流れ

データベース自体の機能。Laravel 以外でも同じ
1

穴あきの命令文を送る

値の場所は ? にしておく

2

DB が命令の形を確定

ここで意味を読み終える。以後、形は変わらない

3

値を別に送る

入力は、命令文とは別の便で届く

4

穴にはめて実行

記号も命令も、ただの文字として扱われる

1つずつ代入する書き方は、コードに書いた行そのものがホワイトリスト。書いていない列には触れないので、DB の初期値がそのまま入る。
——　Laravel の where() は自動で穴あきにしてくれる。危ないのは、自分で文字をつなげて SQL を書いたときじゃ。
まとめ
届いたものを信じない。受け取る枠を、先に決めておく。
列の枠は $fillable、命令の枠はプリペアドステートメント。どちらも「形はこちらが決め、外からは中身だけ」。
