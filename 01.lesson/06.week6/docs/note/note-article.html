教材を見ながらなら、作れる。一覧も、登録フォームも、ちゃんと動く。
でも「自分で機能を1つ足してみましょう」と言われると、手が止まる。

何から始めればいいのか。どのファイルを作ればいいのか。次に何を勉強すればできるようになるのかが分からない。

まさに私もそこで止まりました。

そこでAIを使い整理して分かったのは、コードを書く前に決めておくことがある、ということでした。
それを先に決めると、何を作るかも、作る順番も決まります。

コードの例は Laravel ですが、中心は書き方ではなく「書く前に何を決めるか」です。同じところで止まっている人の、手がかりになればと思います。

▼ 画像：note-0-overall.png をここに入れる ▼

教材のコードは「決め終わった結果」

教材に載っているコードは、誰かが考え終わったあとの結果です。どんな表を作るか。URL をどうするか。データを消したら何が起きるか。そういう「決める」部分は、もう済んだ状態で渡されています。

だから、いくら写しても「決める練習」にはなりません。足りなかったのは知識ではなく、書く前に決める経験でした。

コードを書く前に、決めることがある

たとえば ToDo アプリに、「タスクを細かい手順に分ける機能」を足すとします。

この一文だけでは、1行も書けません。決まっていないことが多いからです。

  • 手順は、1つのタスクに何件まで付けられる？
  • タスクを消したら、その手順はどうなる？
  • 手順の文字は、空でもいい？ 何文字まで？
  • 手順を足したあと、どの画面に戻る？

この質問に答えると、答えがそのままコードになります。Laravel なら、こうです。

  • 「何件でも付けられる」 → 手順用のテーブル（データベースの表）を作り、タスクの番号を書く欄を持たせる
  • 「タスクを消したら、手順も消える」 → ->cascadeOnDelete()
  • 「空はダメ、100文字まで」 → 'title' => 'required|max:100'
  • 「足したあとは、同じ画面に戻る」 → redirect()->route('tasks.show', $task)

1つ目を図にすると、こうなります。

▼ 画像：figs/fig-one2many.png をここに入れる ▼

左が手順、右がタスクの表です。手順の1行ごとに、「どのタスクのものか」を番号で書いておきます（オレンジ色の列）。同じ番号が何回出てきてもいいので、1つのタスクに手順を何件でも付けられます。

教材で写していた1行1行は、誰かが決めたルールの書き写しでした。

そう考えると、コードの読み方も変わります。「この行は、どのルールを書いたものか」。答えられない行が、まだ分かっていない場所です。

考えるのは画面から。作るのはデータから

では、どんな順番で決めるのか。整理すると、こうなりました。

▼ 画像：note-1-flow.png をここに入れる ▼

考えるときは、画面から始めます。

  1. 何がしたい？（使う人の言葉で、1文で）
  2. 画面でどう使う？（どこで何を押して、そのあと何が見えるか）
  3. ルールは？（何件まで、消したらどうなる、空でもいいか）
  4. データの形は？（どんな表や列が要るか）

使う人に見えるのは、画面だけです。画面から考えると、必要なデータが逆算できます。

作るときは逆で、データから始めます。データが無いと、画面は何も表示できず、動いているかも確かめられないからです。

▼ 画像：figs/fig-order.png をここに入れる ▼

図は Laravel の部品の名前で描いてあります。左から、View（画面）、Route（URL と処理を結びつける設定）、Controller（処理を書く場所）、Model（表をコードから扱う窓口）、テーブル（データベースの表）です。画面を開いたときの処理は左から右へ流れ、作る順番はその逆になります。

教材が「まず表の設計から」始まるのは、このためでした。あれは作る順番であって、考える順番ではありません。

最後に、決めたことを1つずつ確かめます。「手順は空ではダメ」と決めたなら、わざと空のまま送ってみる。「タスクを消したら手順も消える」と決めたなら、実際に消して、データベースを見る。9つのステップの図が V の字なのは、左で決めたことを右で確かめるからです。

「結局、何を作ればいいの？」は3つの質問で決まる

整理している途中、私はこう質問しました。

ということは、◯◯を作ろうとしたら、必ず作るのは△△と□□ってこと？

答えは「機能によって変わる」でした。ただ、機能ごとに部品を覚える必要はなく、次の3つを確かめれば決まります。

▼ 画像：note-2-need.png をここに入れる ▼

1. 新しい「もの」が増える？

手順、コメント、プロジェクトのように、何件になるか分からないものが増えるなら、新しい表が要ります。

2. 今あるものに「性質」が増える？

締め切り日や優先度のように、1つのタスクに値が1つだけなら、今ある表に列を足すだけです。新しい表は要りません。

3. 新しい「操作」が増える？

「完了にする」ボタンのように、専用のボタンが要るなら、そのボタンの送り先になる URL と、押されたときの処理が要ります。

3つとも「いいえ」なら、見え方が変わるだけです。たとえば「未完了だけ表示する」は、表も URL も増やさず、一覧を取ってくる処理を少し直せば済みます。

「これは作らなくていい」と判断するのも、設計のうちです。

同じ質問でも、答えが変わるとコードが変わる

▼ 画像：note-3-examples.png をここに入れる ▼

「タスクを手順に分ける」と「タスクをプロジェクトでまとめる」。どちらにも、同じ質問をします。

親を消したら、子はどうなる？

手順なら、タスクを消したときに一緒に消えてほしい。プロジェクトなら、プロジェクトを消しても、中のタスクは残ってほしい。

▼ 画像：figs/fig-project.png をここに入れる ▼

プロジェクトの場合は、タスクの表のほうに「どのプロジェクトのものか」の番号を書く欄が増えます。欄が空（NULL）のタスクは、どのプロジェクトにも入っていないタスクです。

Laravel では、この違いは1語です。

// タスクを消したら、手順も消える
$table->foreignId('task_id')->constrained()->cascadeOnDelete();

// プロジェクトを消しても、タスクは残す
$table->foreignId('project_id')->nullable()->constrained()->nullOnDelete();

でも使う人にとっては、「タスクが全部消えた」か「残っている」かの違いです。コードの量と、決めることの重さは比例しません。

作るときは、細く1本ずつ

決まったら、作ります。全部書いてから動かすのではなく、細く1本通しては確かめます。

  1. 表を作る → データベースを見て、できているか確かめる
  2. 表をコードから扱えるようにする → 1件入れて、取り出してみる
  3. 画面に「表示だけ」を作る → さっき入れた1件が見えるか確かめる
  4. 「追加」を作る → 画面から足せるか確かめる
  5. 「削除」を作る → 消せるか確かめる

追加より先に表示を作るのは、追加できたかどうかを見る手段が先に要るからです。

こうすると、エラーが出ても、原因は直前に書いた数行に絞られます。

途中で「消したときのことを決めていなかった」と気づいて前に戻るのは、失敗ではなく、普通の進み方です。

教材のままでできる練習

新しい教材を探さなくても、今の教材でできることが3つあります。

写し終えたコードを、逆向きに読む

1行ずつ見て、「これはどのルールを書いたもの？」と自分に聞きます。

次の章は、コードを見る前に予想する

見出しだけ読んで、「どんな表が要るか」「URL はどうなるか」を先に書いてみます。そのあとで答え合わせ。予想と違ったところが、まだ分かっていないところです。

自分で足すときは、書く前にメモを埋める

コードを開く前に、この6つを書き出します。

  • 何がしたい（1文で）
  • 画面での操作（どこで何を押して、終わったらどの画面にいるか）
  • やらないこと
  • 何件まで？ 消したらどうなる？ 空でもいい？
  • 増えるのは「もの」「性質」「操作」のどれ？
  • 作る順番と、それぞれの確かめ方

埋まらない行が、「まだ決めていないこと」です。書き始める前に気づけます。

おわりに

「写せるのに、足せない」。整理してみると、これは能力の問題ではなく、考える順番を知らなかっただけでした。

何がしたいかを言葉にする。画面でどう使うかを思い浮かべる。ルールを決める。コードを書くのは、そのあとです。

同じところで止まっているなら、次に機能を足すとき、コードを開く前に「何件まで？ 消したらどうなる？」と自分に聞いてみてください。
