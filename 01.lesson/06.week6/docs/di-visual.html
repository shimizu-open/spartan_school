Laravel / PHP

依存性注入（DI）

Dependency Injection

「使うものを、自分で用意しない」
——　たったそれだけの話です。

01

先に結論から

この1行が分かれば、あとは全部おまけです

必要なものを 自分で作りに行かない。
かわりに 外から受け取る。

これが「依存性注入」と呼ばれているものの正体です

猫先生 名前がいかついだけじゃ。中身は拍子抜けするほど簡単じゃよ。これだけ覚えて帰ればよい。
02

まず言葉をバラしてみる

「依存性注入」は、2つの単語がくっついているだけです

依存性

DEPENDENCY

その仕事をするのに どうしても必要なもの。無いと仕事にならない相棒のこと。

記事ページを表示するには「記事データ」が要る。
→ 記事データが依存性

＋

注入

INJECTION

自分で取りに行くのではなく、外から入れてもらうこと。要するに手渡し。

記事データを自分で探さず、誰かに持ってきてもらう。
→ それが注入

つなげると：「必要なものを、外から入れてもらう」
猫先生 漢字が強そうなだけでのう。普段の言葉に直せば「相棒」と「手渡し」、それだけじゃ。
03

2つのやり方を見比べる

同じ「記事を表示する」仕事を、2通りのやり方で

BEFORE ／ 自分で取りに行く

料理の前に疲れ果てる

畑まで野菜を採りに行き、店で肉を買い、水を汲んでくる。
本題の料理を始める前にヘトヘトです。

AFTER ／ 届けてもらう

座って待つだけ

必要な材料が、お皿に乗って目の前に届きます。
あなたは料理だけに集中できます。

04

これをコードで見ると

消えた2行に注目してください

BEFORE ／ 自分で取りに行く

public function show($id)
{
    // ① まず自分で記事を探しに行く（これが「買い出し」）
    $article = Article::findOrFail($id);

    // ② やっと本題
    return view('articles.show', compact('article'));
}

このメソッドの仕事は「記事を表示する」はずなのに、「記事を探す」という別の仕事まで抱え込んでいます。

AFTER ／ 届けてもらう

public function show(Article $article)
{
    // 記事はもう手元にある。本題だけ。
    return view('articles.show', compact('article'));
}

「探す」行が丸ごと消えました。メソッドは本来の仕事だけをしています。

猫先生 探しに行く足が消えたじゃろう。その足を肩代わりしたのが Laravel なのじゃ。
05

どこで「注文」しているのか

答え：引数に書いた型宣言が、そのまま注文票です

public function show(Article $article)
//                   ↑ ここが注文票

書いてあるのは「Article をください」だけ。
どうやって用意するかは一文字も書いていません。書かなくていい、というのが DI です。

06

注文してから届くまで

/articles/1 を開いたとき、裏側で起きていること

1

アクセス

ブラウザで /articles/1 を開く

2

注文票を読む

Laravel が型宣言を見て「Article が要るのね」と理解

3

用意する

DB から id = 1 の記事を取ってくる

4

手渡し

$article に入れて show() を呼ぶ

07

運んでいるのは誰？

Laravel の中にいる「サービスコンテナ」という執事です

サービスコンテナの仕事は、たった1つだけ。

「欲しい」と言われたものを
用意して、渡す

担当やること
あなた何が欲しいかを書く（＝引数に型宣言を書く）
サービスコンテナどうやって用意するかを全部引き受ける
猫先生 君は注文するだけでよい。作り方を知らなくてよいのじゃ。これを分業という。
08

実は、もう使っていました

気づかないうちに、毎日お世話になっていたやつです

public function index(Request $request)
{
    $q = $request->query('q');   // 検索ワードが取れる
    // …以下省略
}

Request $request も、まったく同じ仕組みです。
$request を作るコードはどこにも書いていないのに、中には送信されたデータが全部入っています。

引数に書いたもの実際に届くもの
Request $requestブラウザから送信されたデータ一式（検索ワード、フォーム入力など）
Article $articleURL の番号に対応する記事 1 件
猫先生 ほれ、知らぬ間にずっと使っておったじゃろう。新しい話を覚えたのではなく、名前を知っただけなのじゃ。
09

で、何が嬉しいの？

3つあります

1

コードが短くなる

「探す」「作る」の行がまるごと消えます。本題だけが残るので、見通しがよくなります。

2

読めば分かる

引数を見るだけで「この処理は何に頼っているか」が一目で分かります。中身を読まなくて済みます。

3

差し替えられる

テストのとき、本物の代わりにニセモノを渡せます。メソッドの中身は1文字も変えずに済みます。

まとめ

「自分で取りに行く」のをやめて、
「注文する」に変える。
それが依存性注入。

むずかしいのは名前だけでした。やっていることは、注文票を書いて待つことだけです。

補足：正確に言うと

  • Article $article のようにモデルを受け取る仕組みには、「ルートモデルバインディング」という専用の名前もついています。DI の土台の上に乗った、Laravel 独自の便利機能です。
  • Request $request のほうが、より素直な DI の例です。こちらは Laravel に限らず、多くのフレームワークで見かける形です。
  • どちらも「引数の型宣言を見て、Laravel が用意して渡す」という点はまったく同じです。まずはここだけ押さえておけば十分です。
