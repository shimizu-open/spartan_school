倉庫と受付係、二通の手紙
— S3とCloudFrontの誤解録 —

Case No.1 に先立つ調査の記録 · S3 / CloudFront / Origin / CNAME

これは Case No.1(独自ドメインとHTTPSの謎)に着手する前、S3とCloudFrontの関係を巡って抱いた数々の誤解と、その解消の記録である。「Static website hosting が Disabled なのにサイトが見えるのはなぜか」「Origin domain とは何者か」「CNAMEが二種類あるように見える」——当時の疑問は、どれも本質を突いていた。

I.S3には二つの顔がある — 「Webサイト」と「倉庫」

最初の謎はこれだった。S3の画面で Static website hosting: Disabled なのに、独自ドメインでサイトが表示される。矛盾ではないのか?

答え:S3の使い方は二通りあり、今回の構成では静的ウェブサイトホスティング機能を使っていない。

パターンA:S3自体を公開パターンB:CloudFrontの裏の倉庫(今回)
Static website hostingEnabled にするDisabled でよい
使われるURLbucket.s3-website-リージョン…
(website endpoint)		bucket.s3.リージョン.amazonaws.com
(通常のバケットエンドポイント)
S3の役割Webサイトの表玄関ファイル置き場(倉庫)

CloudFrontはS3を「Webサイト」として見ていない。「index.html をください」→「はい、どうぞ」——ただファイルを取りに行くだけである。つまり:

S3 = ファイルを保管する倉庫
CloudFront = 外から来る客を受け付ける入口(受付係) — 本件の根本原理

むしろ本番構成では、S3を公開せずCloudFront経由のみ許可する(OAC)のが定石。倉庫の扉は受付係にしか開かない方がよいのだ(この仕組みの詳細は Case No.2 に記録した)。

❦ ❦ ❦

II.Origin domain の正体 — 照合ではなく、保存された一行の文字列

次の疑問。「CloudFrontのOrigin domainに書かれている内容が、S3側にはバラバラに書いてある。CloudFrontはそれを集めて照合しているのか?」

分解すると確かにそう見える:

my-bucket.s3.ap-northeast-1.amazonaws.com
└──┬───┘ └┬┘ └─────┬──────┘ └────┬────┘
バケット名  S3  リージョン(東京)  AWSのドメイン

S3画面では: Bucket name: my-bucket / Region: ap-northeast-1 と別々に表示

しかし答えは否。CloudFrontは毎回S3の画面を見て組み立てているのではなく、ディストリビューション設定に「Origin domain」という一つの文字列として保存されているだけである。設定した瞬間に写し取られた住所録であり、以後S3側と自動照合はされない。

どこで見るか(目的別の索引)

見たいもの見る場所
CloudFrontがどのS3へ取りに行くかCloudFront → Distribution → Origins → Origin domain(ここが本命)
その元になるS3情報S3 → Bucket → Bucket name / Region
CloudFrontに与えた入場許可S3 → Bucket → Permissions → Bucket policy(OACの許可JSON)
設定全体をJSONでaws cloudfront get-distribution-config --id ID → Origins.Items[].DomainName

オリジンとは「CloudFrontが元データを取りに行く場所」=原本置き場。CloudFrontは常にS3へ行くわけではなく、エッジにキャッシュがあれば即返し、無いときだけオリジンへ赴く。「最終的にS3にアクセスが行く」とは「キャッシュに無いとき、代理で取りに行く先がS3」という意味である。

❦ ❦ ❦

III.二通の手紙 — CNAMEは二種類ある

調査中もっとも混乱したのがここである。CNAMEという言葉が二つの全く違う場面に現れる。

まずCNAMEとは、DNSレコードの一種で「この名前は、あちらの名前の別名です」という意味に過ぎない(Aレコードが「名前→IPアドレス」なのに対し、CNAMEは「名前→別の名前」)。だが本件では、用途の異なる二通が登場する:

① 案内用CNAME② ACM検証用CNAME
形www.example.com → dxxxx.cloudfront.net_ランダム.example.com → _ランダム.acm-validations.aws
目的訪問者をCloudFrontへ案内する「私はこのドメインのDNSを操作できる=持ち主」だとACMに証明する
誰が読む世界中のブラウザACM(認証局)だけ
消してよいか消したらサイトに繋がらない置きっぱなしにすると証明書が自動更新される(推奨:残す)

②が必要な理由:もし誰でも他人のドメインの証明書を取れたら、google.com の証明書を貰って偽サイトが作り放題になる。ゆえにACMは「このランダムなCNAMEをDNSに置けるなら本人」という試験を課す。ユーザーのアクセス経路は一切変わらない。あれは検証専用の暗号めいた合言葉である。

正しい発行の順序(当時、順番を誤解していた)

ACMで証明書を申請
  → Pending validation(保留)
  → ACMが検証用CNAME(②)を提示
  → それを Route 53 に登録
  → ACMがDNSを確認 → 証明書 Issued(発行済み)
  → その証明書を CloudFront に取り付ける
  → CloudFrontに Alternate domain name を登録
  → Route 53 に案内用レコード(①)を作成
⚠ 当時の誤解 「CloudFrontにCNAMEを登録することでドメイン管理者だと証明され、証明書が発行される」と思っていたが、これは逆。証明はRoute 53上の検証用CNAME(②)で完了し、発行済みの証明書を後からCloudFrontに付けるのが正しい順序である。

IV.CloudFront側のCNAME欄は「許可リスト」

ではCloudFrontの設定にある「CNAME(代替ドメイン名)」とは何か。これはDNSレコードではなく、受付係の来客名簿である。

  • CloudFrontには生まれつき本名がある:dxxxx.cloudfront.net。この名前なら無条件で受け付ける
  • 独自ドメイン名で訪ねて来た客を受け付けるには、「この名前で来た客も私宛だ」という登録(Alternate domain name)が必要
  • 登録が無いと、DNSの案内が正しくてもCloudFrontが「その名前は取り扱っていない」と門前払いする(403)
  • そしてこの登録には発行済みACM証明書の添付が必須。他人のドメインを勝手に名簿へ書けない仕組みになっている

Route 53側のCNAME/エイリアスが「道案内」、CloudFront側のCNAMEが「受付名簿」。同じ語だが役割はまるで違う。

❦ ❦ ❦

V.HTTPSはどこで終わるか — リダイレクトと提供の違い

最後の誤解:「S3でHTTPからHTTPSにリダイレクトできるなら、ACMは要らないのでは?」

これは「HTTPSへ案内すること」と「HTTPSを提供すること」の混同である。

  • リダイレクト = 「その用件はあちらの窓口へ」と案内する行為。案内した先でHTTPSを受けられる者が必要
  • HTTPSの提供 = 証明書と秘密鍵を持ち、TLSハンドシェイクに応じる行為(Case No.1 参照)
  • S3のwebsite endpointはHTTPSを受けられない(HTTPのみ)。ゆえに独自ドメインのHTTPSは成立しない
  • 証明書(ACM)を取り付けられるのはCloudFront。だからHTTPS化とは「S3の前にCloudFrontを置き、そこで暗号化を終端させる」ことを意味する
◆ 結び — 前日譚で得た三つの武器 ①S3は倉庫、CloudFrontは受付係。倉庫が表玄関を持つ必要はない。 ②Origin domainは保存された一行の住所。照合の魔法は存在しない。 ③CNAMEという語が出たら「案内用か、検証用か、それとも受付名簿か」を問え。 この三つの武器を携えて、Case No.1 の捜査は始まった。
